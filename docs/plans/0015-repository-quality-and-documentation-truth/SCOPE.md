# Plan 0015 — Repository Quality, Release Integrity, and Documentation Truth

> Make a green change and a published release mean every supported row, locked graph, acquired tool, cache input, retained decision, and delivered archive was independently checked, and make product documentation state exactly what repository authorities state now.

## Why this plan

The main quality workflow is broad but Linux-only. The native workflow is the only macOS execution and runs after push, not on pull requests, with one narrow integration target. The excluded fuzz workspace has its own lockfile, but dependency policy reads only the root graph. At the same time, root documentation describes a third unsupported target, absent metadata and release machinery that now exist, and configuration the product allegedly never reads even though the CLI loads profiles.

These are assurance failures rather than cosmetic drift. A green pull request cannot exclude a supported operating system or an executable dependency graph, and a completed documentation review cannot remain evidence after the facts it reviewed change.

The release path has the same class of incomplete evidence at a more consequential boundary. Downloaded automation tools execute before their bytes are authenticated; required cache inputs can be checked for existence without entering the cache identity; the acceptance verifier trusts most identities and report digests stated by its own manifest; and publication accepts any non-empty set it finds from an ambient checkout without requiring the complete supported-row set or accepted decision. Each can be green while proving less than its interface claims.

## In scope

- **0060 — Complete change and release evidence.** Every supported native row gates pull requests; both independently locked graphs and every duplicate exception pass repository policy; downloaded automation tools authenticate before execution; one provenance-bound cache reaches every release row; acceptance is checked against independent retained evidence; and publication admits exactly one complete tag-pinned supported-row set before any provider mutation.
- **0061 — Present factual product prose.** Supported targets, package metadata, profile consumption, release availability, and automation claims are derived from or exactly compared with their committed authorities. Review records are revision-bound evidence, not permanent assertions.

## Out of scope

This plan does not add a supported platform, publish a package, grant hosted publication permission, change signing-key custody or the attestation trust root, or change the dependency allow-list. Publication remains an operator action; the plan closes what that action must verify. Plans 0011 and 0014 remain unchanged predecessor bundles; this plan owns only the follow-on gaps found by review. General copy editing and historical plan prose remain outside the product-document contract.

## Review evidence at `2808354`

- `.github/workflows/platform-runtime.yml` has only a `push` trigger and runs `platform_runtime_contract` for Linux and macOS. `.github/workflows/quality.yml` runs the full workspace gate only on Ubuntu. `github_workflow_contract.rs` checks matrix shape but not pull-request coverage or command breadth. Thus macOS-specific compilation outside one test can fail only after merge.
- The root workspace excludes `fuzz/`, which has its own `Cargo.lock` and packages absent from the product lock. `scripts/quality` invokes `cargo deny` only for the root manifest, and `toolchain_and_dependency_policy.rs` checks only root lock checksums. `deny.toml` also treats duplicate versions as warnings with no structured exception inventory, so new duplication exits successfully. Completed Plan 0009 task `3801-minimum-rust-and-dependency-gates` explicitly requires both graphs and narrow documented duplicate exceptions.
- `README.md` and `ARCHITECTURE.md` say three target rows exist, packages lack license/repository metadata, release evidence is absent, and profiles are not read. `support/platforms.toml` has two rows; workspace package metadata carries license and repository; release workflows/scripts exist; and `command_line.rs` calls `load_profiles` in product composition. `product_documentation.rs` uses subset/token checks that accept the extra row and even requires stale phrases, while `DOCUMENTATION_REVIEW.md` presents an earlier factual review without a revision boundary.
- `scripts/install_pinned_repository_tools` downloads and extracts ShellCheck and the GitHub CLI before asking the resulting executables for their versions; `support/repository-tools.toml` carries no archive identities. `scripts/build_release_notes` separately hard-codes `git-cliff 2.14.1` and either trusts an ambient binary that reports that version or installs it from the network. Self-reported compatibility does not authenticate bytes before execution.
- `.github/workflows/release.yml` prepares the purported common cache independently in every matrix row and uploads only the coordinator copy. Every row builds and passes a coverage-fuzzing bundle to `scripts/prepare_locked_source_cache`, but preparation only checks the path exists: it does not copy, hash, record, verify, or exercise the bundle. The required input therefore changes no cache identity or acceptance result. `release_input_cache::survey` also follows and digests a link target where release-acceptance evidence now refuses any link, so the two authorities disagree about the same tree.
- `AcceptanceManifest` records the source tree, provider-reported workflow identity, coordinator row, three input digests, and a digest for every gate report. `verify-release-acceptance` compares only the source commit, gate names/order/outcomes, and overall outcome; it does not independently inspect the other identities, inputs, or retained report bytes. Mutating those self-stated fields or replacing a retained report leaves verification successful.
- `scripts/publish_release` accepts any non-empty subset of child directories containing archives and never requires the separately retained release-acceptance artifact. It uses verifier code and policy from the ambient checkout, resolves only the local tag, and does not require clean `HEAD`, local peeled tag, remote peeled tag, and accepted source commit to agree before provider mutation.
