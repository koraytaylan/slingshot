# Plan 0004 — Daemon Runtime and Local Protocol

> Make one durable daemon the local authority for one selected profile and environment, then prove every command-line process can find it, share it, and recover its work after interruption.

## Why this plan

Plans 0002 and 0003 provide validated target configuration and typed commands, but neither gives those commands a durable execution home. Starting work directly in each command-line process would split ownership across short-lived clients, make retries ambiguous, and leave no stable process for Model Context Protocol sessions or workflows to observe. This plan establishes the local execution boundary before remote author communication exists: a retained control protocol, versioned operation protocols, a per-target daemon singleton, durable target-partitioned operation and artifact state, automatic startup, fair scheduling, progress fan-out, bounded inspection and maintenance, and restart recovery.

The product daemon in this plan uses an unavailable executor and never simulates remote success. An internal `test-daemon` subcommand of the existing `slingshot-development` binary injects a fake executor to exercise the complete operation lifecycle without adding any part of the separately developed Java agent contract to the product graph or adding a third workspace binary. Plan 0005 supplies authenticated author-only transport through the same executor boundary.

## In scope

- **0014 — Module Inventory and Versioned Local Protocol.** Adopt Plan 0001's crate and structural family roots, preserve and classify its retained behavioral and process-entry leaves, register each genuinely new Plan 0004 library leaf as a compiling documentation-only module, prove the workspace retains exactly the two Plan 0001 binaries, and make every behavioral task descend from that single scaffold before it changes a leaf; then commit one canonical versioned `DaemonRuntimeContract` manifest and digest as the only source for Plan-0004-owned public values, consume Plan 0001's embedded typed `support/foundation-contract.toml` values without redeclaring them, extend its retained `daemon.ping` and current-nonce `daemon.stop` control independently of versioned execution messages, and define operation-free target-qualified maintenance-result identity, metadata, and read envelopes, digest/target/revision matching, structured errors, and byte-exact transcripts shared by daemon and client.
- **0015 — Durable Operation State.** Define the operation lifecycle and conditional terminal evidence, a target-and-SelectedEnvironmentRevision-bound canonical command fingerprint, persistent installation identity, target/revision-checked SQLite schema and repository, selected-revision-bound durable recovery-resume receipts plus maintenance-application receipts and target-qualified maintenance-result associations, conservative transactional row/artifact capacity, exact header-and-frame-aware database/WAL/SHM/transaction/reader/checkpoint physical bounds, a pinned memory-only transient policy enforced by a closed SQL inventory and restrictive VFS object whitelist, deterministic artifact slots, and checksum-verified artifact storage.
- **0016 — Runtime Ownership and Startup.** Derive a manifest-bounded secure runtime namespace for each `(profile, environment)`, enforce one daemon owner, keep process identifiers diagnostic-only, recover stale endpoint state safely, require `PIPE_REJECT_REMOTE_CLIENTS` on every Windows named-pipe server creation, consume one immutable Plan 0002 selected-environment snapshot only after its exact committed-generation proof, use its target hash directly without rehashing, retain its distinct platform-only `VerifiedIdentityManagementTrustPolicyIdentity` and platform-plus-selected-additional-author `VerifiedAuthorTrustPolicyIdentity` with their exact route-typed root snapshots for daemon lifetime without DER-only widening or cross-use, refuse unsafe identity/target/revision recovery before readiness or admission, provide secure bounded diagnostics, and let concurrent clients start or join the owner.
- **0017 — Operation Service and Scheduling.** Keep production execution explicitly unavailable until Plan 0005, inject a fake only through the existing development binary's internal test-daemon subcommand, admit and schedule work under manifest-owned bounded capacity, expose bounded list/status/result/progress services, resume explicitly paused recovery through durable source-receipt replay, resolve current operation-free maintenance metadata before transferring verified operation artifacts and maintenance results through resumable chunks whose nonzero offsets first authenticate the exact same-handle prefix, provide complete canonical terminal-maintenance preview and durable apply replay as local services, dispatch control independently of operation compatibility, and stop without losing recoverable work.
- **0018 — Restart and Process Proof.** Inject interruption at durable and physical-storage boundaries through the internal test-daemon subcommand, including pinned-reader/write-churn/checkpoint backpressure, exercise simultaneous client startup in real processes, clean up through current-nonce cooperative stop or the spawning supervisor's retained instance-bound child/native handle without process-identifier signalling, prove stale nonces cannot affect replacements, freeze a digest-bound golden local session, and document only the daemon behavior proved at the end of the plan.

## Plan dependencies

Plan 0001 supplies the ten crate roots, structural module families, retained behavioral leaves, two process entries, inward dependency map, frozen capability inventory, and platform adapters. Task `daemon-runtime-module-scaffold` adopts the seven roots used here, preserves the predecessor-owned behavioral leaves and development process entry unchanged, and owns the exact declaration inventory and documentation-only shells for genuinely new Plan 0004 library leaves without changing a manifest or dependency. The new test-daemon source is one declared development-library leaf, while task `operation-executor-boundary` extends the existing exhaustive development dispatcher with its internal subcommand; neither task creates a Cargo target. `daemon-runtime-contract` is the only former bundle-local graph root and now depends on that scaffold, so every other Plan 0004 task reaches it transitively. The scaffold test proves the fixture/declaration/source/footprint bijection for every new library leaf, classifies every adopted leaf exactly once, retains exactly the two Plan 0001 binaries, and requires ancestry for every overlapping feature source footprint. Plans 0002 and 0003 remain sequential-registration inputs that supply the immutable selected environment and typed command catalog; no task frontmatter creates a cross-bundle dependency.

## Out of scope

Hypertext Transfer Protocol submission to an author, Server-Sent Event consumption, heartbeat supervision, Adobe Experience Manager authentication, and remote Sling Job reconciliation belong to Plan 0005. The Java `slingshot-agent` implementation remains outside this repository. The complete human command-line surface and standard-input/output Model Context Protocol server belong to later plans; this plan supplies their daemon client boundary. Plan 0004 runs deterministic platform-policy fixtures and at most the one native row matching its current environment; Plan 0009 owns provider-authenticated all-supported-row release evidence. A daemon never connects to a publisher, and this local-only plan makes no remote connection at all.
