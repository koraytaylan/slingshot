## Normative daemon-runtime contract

Task `daemon-runtime-contract` first commits canonical `policy/daemon-runtime-contract-1.json` with format literal `slingshot.daemon-runtime-contract/1` and companion `policy/daemon-runtime-contract-1.sha256`. The JSON is UTF-8 without a byte-order mark, contains exactly `format`, `operation_protocol_version`, `limits`, and `formulas`, uses byte-lexicographically ordered ASCII object keys, unsigned minimal base-ten integers, no insignificant whitespace, and one final line feed. The sidecar is exactly the SHA-256 digest of those complete JSON bytes as 64 lowercase hexadecimal bytes plus one line feed. Repository bytes, embedded bytes, the typed read-only `DaemonRuntimeContract`, schemas, storage settings, fixtures, documentation, and independently implemented consumers must agree; missing, additional, reordered, differently valued, locally redeclared, or fallback public values fail construction. The contract has no deployment override. Changing one value requires a new operation-protocol version and a new manifest format rather than silently changing version `1`.

The manifest formulas are exact. Database bytes are `4,096 * 262,144 = 1,073,741,824`. One write transaction changes at most `4,096 * 4,096 = 16,777,216` database bytes and appends at most `4,096 * (24 + 4,096) = 16,875,520` WAL bytes. A nonempty maximum WAL is its one 32-byte file header plus `16,384 * (24 + 4,096)` frame bytes, or `67,502,112`; it is not page count multiplied by page size. The write high-water is `67,502,112 - 16,875,520 = 50,626,592`, so refusing a new maximum transaction at or above that length cannot cross the WAL cap. Maximum physical bytes are `1,073,741,824 + 67,502,112 + 262,144 = 1,141,506,080`. Replacement physical bytes are `2 * 1,073,741,824 + 67,502,112 + 262,144 = 2,215,247,904`. Diagnostic total is file bytes times retained files, and individual artifact bytes are the checked maximum of Plan 0003's declared remote artifact slots and `MAXIMUM_CANONICAL_STRUCTURED_RESULT_BYTES`. Every equation is checked in unsigned 64-bit arithmetic, and independently authored arithmetic vectors calculate each operand and result without using the production formula implementation. The filesystem safety reserve equals the complete replacement-physical maximum so a migration or checkpoint cannot consume artifact capacity promised to operations.

`DaemonRuntimeContractDigest` is the sidecar value. `Hello` advertises it without making retained control dependent on equality; every versioned operation envelope carries the caller's expected value, every admitted operation and maintenance receipt persists it, and operation dispatch/startup recovery refuse a mismatch before repository mutation, executor access, or network access. A terminal record under an older digest remains read-only history, while no nonterminal record is upgraded in place. Plan 0006 and Plan 0007 must consume this digest when constructing local requests and presenting maintenance results.

## 0014 — Module Inventory and Versioned Local Protocol

Task `daemon-runtime-module-scaffold` first establishes the compiling source tree and exact ownership/dependency evidence above. Task `daemon-runtime-contract`, the former graph root, depends directly on it; all local-protocol, persistence, runtime, service, process, and documentation tasks descend through that edge.

`slingshot-local-protocol` is the sole wire contract between local clients and `slingshot-daemon`. Its existing frame prefix, byte order, payload/nesting/collection bounds, identifier/error bounds, and progress semantics are read from the embedded typed `FoundationContract`; Plan 0004 extends the codec without restating a numeric value or accepting a caller-supplied replacement. The frame codec accepts fragmented reads and writes, rejects zero-length, oversized, truncated, trailing, and invalid UTF-8 frames, never allocates from an unchecked peer value, and exposes zero-bytes/partial-prefix/partial-payload progress so server deadlines do not reparse input.

The stable local control envelope is independent of every operation-protocol revision. It preserves Plan 0001's manifest-versioned wire methods `daemon.ping` and `daemon.stop` and extends their typed surface with `Hello` and `DaemonStatus`; operation-protocol evolution cannot replace or reinterpret either retained method. `Hello` returns the daemon product version, runtime namespace, instance nonce, selected `AuthorTargetIdentity`, `SelectedEnvironmentRevision`, `DaemonRuntimeContractDigest`, and the closed set of supported operation-protocol versions. `daemon.stop` requires the exact live nonce learned from that instance; a stale nonce returns `stale_daemon_instance` without stopping admission, closing the listener, removing readiness, signalling a process, or otherwise affecting a replacement. A client whose operation version or daemon-runtime digest is unsupported can still inspect daemon status and explicitly stop that daemon. Unsupported operation versions or a digest mismatch return a structured incompatibility response without disabling the control connection; no side guesses, silently downgrades, routes to another daemon, or stops an owner automatically.

Each versioned operation envelope contains its operation-protocol version, exact expected `DaemonRuntimeContractDigest`, caller-created request identifier, expected `AuthorTargetIdentity`, expected `SelectedEnvironmentRevision`, and exactly one request. The request set is `Execute`, `OperationStatus`, `ListOperations`, `Wait`, `Result`, `ResumeOperationRecovery`, `ArtifactRead`, `MaintenanceResultMetadata`, `MaintenanceResultRead`, `TerminalMaintenancePreview`, and `TerminalMaintenanceApply`. Every execution-capable client sends the digest plus both identity values from its typed contracts and Plan-0002 selection. A mismatch is refused before repository or executor access with bounded guidance to update or stop and restart the named daemon explicitly.

`Execute` carries the caller-created operation identifier, selected command, and optional workflow correlation identifier. Point and wait requests carry the target digest plus operation identifier. `ListOperations` carries bounded filters, a named page-size limit, and an optional opaque versioned cursor. `ArtifactRead` carries an `ArtifactIdentifier`, expected digest, starting byte offset, and preferred decoded chunk byte length bounded by `MAXIMUM_LOCAL_ARTIFACT_CHUNK_BYTES`. `MaintenanceResultMetadata` is keyed only by explicit `AuthorTargetIdentityDigest` plus `MaintenanceResultIdentifier`; it has no expected content digest, operation identifier, artifact slot, byte offset, or path. Its same-named success response returns only the currently readable association's target and identifier, preview/application kind, reviewed source digest, content digest, exact byte length, fixed `application/json`, association revision, and current-preview or application-receipt retention owner. `MaintenanceResultRead` carries that explicit target and identifier plus the metadata-supplied or caller-supplied expected content digest, starting byte offset, and the same bounded preferred decoded chunk length; it likewise has no operation identifier or artifact slot. Maintenance preview carries one explicit author-target partition plus bounded terminal and prior-application-receipt selection criteria; apply carries that same partition and the returned preview digest. `daemon.stop` remains a retained control request outside operation-version negotiation. The connected namespace is contextual routing information; only equality with the exact current hello/readiness nonce authorizes that instance transition, and neither a target value nor a process identifier can substitute for it.

Responses distinguish accepted, replayed, unavailable executor, current status, bounded list page, progress, conditional-evidence recovery-required status, conditionally dispositioned terminal result, artifact start/chunk/end, maintenance-result metadata, maintenance-result start/chunk/end, complete maintenance preview, maintenance applied/replayed receipt, daemon stopping, target or revision mismatch, scheduler-capacity exhaustion, persistent-capacity exhaustion with bounded usage/limit and maintenance guidance, identifier conflict, missing operation, invalid transition, incompatible operation protocol, malformed frame, and internal failure. Only `ArtifactChunk` and `MaintenanceResultChunk` carry bytes, using the standard padded Base64 alphabet below both named limits; terminal results carry checksum-verified artifact metadata.

## 0015 — Durable Operation State

`slingshot-domain::operation` defines a total fold over `queued`, `submitting`, `accepted`, `running`, `succeeded`, and `failed`. Connection health and retry scheduling are separate durable recovery facts rather than lifecycle states. Each accepted lifecycle, progress, certainty, or recovery fact increments a durable operation revision. The latest progress value is bounded and stored with the revision that introduced it. `succeeded` and `failed` are immutable terminal states; duplicates carrying identical facts are no-ops, and conflicting or regressive facts are rejected without mutation.

`OperationExecutionCertainty` is the single uncertainty vocabulary consumed unchanged by Plan 0005: `ConfirmedNotExecuted`, `SubmissionUnknown`, or `RemoteOutcomeUnknown`. It never encodes a known successful remote outcome. Nonterminal `RecoveryRequired` instead carries a conditional `RecoveryExecutionEvidence` union: `ExecutionCertainty` contains exactly one OperationExecutionCertainty while execution remains unproved, and `AuthoritativeRemoteSuccess` contains no certainty field when remote execution is proven successful but required result validation, local externalization, or artifact acquisition remains incomplete. `OperationExecutorOutcome` has closed `Succeeded`, `TerminalFailure`, and `RecoveryRequired` variants. Terminal failure has a closed `TerminalFailureKind`—`Rejected`, `RemoteFailed`, `ResultUnavailable`, `RecoveryWindowExpired`, `RemoteStateLost`, `IntegrityFailure`, or `RetryPolicyExhausted`—and a conditional `TerminalFailureDisposition` union: `AuthoritativeNonExecution` carries exactly `ConfirmedNotExecuted`; `AuthoritativeRemoteFailure` carries no certainty field; `AuthoritativeRemoteSuccess` carries no certainty field; and `FailClosedIndeterminate` carries exactly `SubmissionUnknown` or `RemoteOutcomeUnknown`.

The combination is validated rather than inferred. `Rejected` and terminal `RetryPolicyExhausted` require `AuthoritativeNonExecution` with `ConfirmedNotExecuted`. `RemoteFailed` requires `AuthoritativeRemoteFailure` and structurally cannot carry a certainty field; neither unknown nor manufactured confirmed-nonexecution certainty is a substitute for remote terminal proof. `ResultUnavailable` requires `AuthoritativeRemoteSuccess` and proves the command reached remote success even though its required result or artifact cannot be obtained or validated; it carries no certainty and never rewrites that success as unknown execution. `RecoveryWindowExpired` is legal only when a retained operation mapping retires before terminal remote truth is known; `RecoveryWindowExpired`, `RemoteStateLost`, and `IntegrityFailure` use `FailClosedIndeterminate` and retain `SubmissionUnknown` or `RemoteOutcomeUnknown` inside that disposition. They are terminal local fail-closed dispositions without masquerading as authoritative remote outcomes, and a result/artifact retention expiry after proven remote success can only be `ResultUnavailable` with `AuthoritativeRemoteSuccess`. Exhausted retry policy with unknown certainty remains nonterminal `RecoveryRequired` carrying `ExecutionCertainty`. Status and result expose kind plus exactly one legal disposition payload. Slingshot never labels a domain-specific compensation safe; workflow policy interprets the truthful execution facts.

A recovery fact also records one RecoveryExecutionEvidence, bounded category, attempt count, retry observation UTC value, bounded retry delay, checked UTC diagnostic deadline, explicit manual-resume eligibility, and bounded redacted detail. Ambiguous submission, event reconnection, operation lookup, and job-snapshot recovery carry `ExecutionCertainty`; post-success result acquisition, artifact transfer, and `PersistentCapacityUnavailable` carry `AuthoritativeRemoteSuccess`. Illegal category/evidence combinations are unconstructible and rejected on the wire and at storage reopen. While the process lives, the observation creates a checked monotonic deadline. On startup, injected UTC and monotonic clocks reconstruct it: elapsed wall time is clamped between zero and the original delay, remaining delay cannot exceed the original delay, and checked addition anchors that remainder to the new monotonic clock. Backward clock movement can wait at most the original delay; forward movement can make the retry immediately eligible. Idempotency and correctness never depend on exact eligibility timing. A later retry/reconciliation clears or replaces facts under revision compare-and-set.

A manually resumable automatic-policy or persistent-capacity pause is resumed only by versioned `ResumeOperationRecovery`. After the ordinary current-daemon target and selected-revision gate, the service computes a bounded source fingerprint from the target partition, exact `SelectedEnvironmentRevision`, operation identifier, expected operation revision, and exact expected recovery category. It first looks up a durable `RecoveryResumeReceipt` by that source fingerprint. An exact committed receipt and the operation's truthful current status are read in one repository snapshot before current lifecycle/category validation; replay requires the receipt's stored selected revision to equal both the request and operation and returns the recorded applied revision plus that status even after later progress, another recovery cycle, or terminal settlement. Concurrent terminal maintenance therefore linearizes either after the replay snapshot or before it removes both operation and child receipts, never between receipt lookup and status. A fresh source then performs compare-and-set against the current manually resumable recovery fact and exact stored selected revision, preserves the existing revision-bound command fingerprint and every operation/remote identity, records scheduler eligibility and a new receipt atomically, and increments the operation revision once; it allocates no identity, invokes no executor, and submits no work. Competing, stale, or wrong-revision fresh preconditions conflict unchanged.

Receipts are target-partitioned children of the operation and remain through restart until explicit terminal maintenance removes that operation. `MAXIMUM_RECOVERY_RESUME_RECEIPTS_PER_OPERATION` is derived from the closed bounded recovery-attempt policy; fresh resumption beyond that limit is refused without mutation, while an exact stored replay remains available. Multiple permitted recovery cycles retain distinct source receipts, and concurrent exact calls converge on one applied receipt. Plan 0004 persists/exposes this state; Plan 0005 owns the live retry scheduler and remote reconciliation policy.

`InstallationIdentifier` is a persistent random value in one secure global user-state record. The same atomically replaced record contains a registered-target ledger with `initializing` and `registered` entries, and each target database stores the identifier. One global installation-state lock serializes first start and target registration across different namespace daemons. Initial identifier creation is synchronized and permitted only when the entire Slingshot state root is demonstrably empty. New-target startup records `initializing`, creates/synchronizes the database with the same identifier, then marks `registered`, all while holding the global lock. A crash with an `initializing` entry may resume only when the absent or present database exactly matches that staged state; every other missing, corrupt, mismatched, unregistered-database, or registered-with-missing-database combination refuses before readiness and leaves bytes unchanged. Identity recovery is an explicit operator action outside this plan; the daemon never silently creates a replacement that strands remote subscriptions. Every admitted operation persists its InstallationIdentifier snapshot in the same transaction as `queued`, before executor invocation or any possible remote input/output. Plan 0005 reads that immutable operation-owned snapshot when it later derives agent and subscription identifiers.

The repository key is `(AuthorTargetIdentityDigest, OperationIdentifier)`, not a profile/environment namespace plus operation identifier. Plan 0004 consumes Plan 0002's complete typed `AuthorTargetIdentity` and `SelectedEnvironmentRevision` as opaque exact values without reproducing or inspecting their preimage fields. The repository uses Plan 0002's SHA-256 output as `AuthorTargetIdentityDigest` directly; it never hashes the lowercase rendering or otherwise applies a second digest. Plan 0002's raw `ProfileAuthenticationContractDigest` is already bound inside both opaque target and revision, and the immutable platform-only `VerifiedIdentityManagementTrustPolicyIdentity` and distinct platform-plus-selected-additional-author `VerifiedAuthorTrustPolicyIdentity` are already bound inside the revision; Plan 0004 neither extracts nor redeclares those fields. The stable target digest partitions operation rows, artifact-slot associations, status, wait, result, and maintenance. When Plan 0002 reports genuine same-principal secret/key/certificate/token rotation, both supplied target and revision remain stable. A supplied revision change preserves the target partition but selects another security context; another supplied target selects another partition even when profile, environment, credential source, and author address are unchanged. Current execution selects only the current target partition and exact revision. Startup audits every partition and refuses if any nonterminal row belongs to another target or revision. Terminal old-target/revision history remains queryable, listable, and maintainable, and its summaries expose target/revision digests without raw principal values.

`slingshot-domain::command_fingerprint` hashes a versioned canonical encoding of the complete opaque Plan 0002 `AuthorTargetIdentity`, exact `SelectedEnvironmentRevision`, and typed command content. It does not rebuild the target from deployment, address, principal, or contract fields and does not replace `AuthorTargetIdentityDigest` with a hash of its rendering. Repeating an identifier within the same target partition returns the existing operation only when both revision-bound fingerprint and separately stored revision match; different command content or revision conflicts. The same caller identifier can name independent work in distinct target partitions without collision. Wait cursors, connection identifiers, timestamps, and display preferences are excluded. Genuine same-principal credential rotation leaves the Plan 0002 revision and fingerprint stable; a canonical metascope, `VerifiedIdentityManagementTrustPolicyIdentity`, or `VerifiedAuthorTrustPolicyIdentity` change alters the included revision while preserving target identity, and a principal or profile-authentication-contract change arrives as changed opaque target/revision values. The selected revision remains stored separately as independently checked startup-snapshot provenance rather than being trusted only through the fingerprint.

`slingshot-storage` owns one SQLite database per name-derived runtime namespace below the platform's persistent per-user Slingshot state root and depends only on `slingshot-domain`. Migrations are ordered, transactional, and monotonic; a database whose schema is newer than the binary is refused without mutation. The schema stores the installation-identifier snapshot, target digest and full immutable identity, exact selected-environment revision, operation identifier, revision-bound fingerprint, command payload, lifecycle and progress revisions, bounded progress, enqueue order, caller identity, workflow correlation, conditional recovery execution evidence, retry observation/delay/diagnostic facts, bounded target-and-revision-bound recovery-resume receipts, result disposition, the conditional terminal failure union, bounded failure metadata, timestamps, artifact-slot references, bounded target-partitioned maintenance-application receipts, and target-qualified maintenance-result associations. `MaintenanceResultAssociation` is independent of operation rows, keyed by `(AuthorTargetIdentityDigest, MaintenanceResultIdentifier)`, and carries kind, reviewed source digest, content digest, exact byte length, `application/json`, artifact-blob reference, association revision, and either current-preview or application-receipt retention ownership. Operation admission, exact target/revision replay/conflict detection, and initial `queued` persistence happen in one transaction. An index over target digest, descending enqueue sequence, and operation identifier supports stable bounded listing and opaque cursors without scanning payloads.

The single daemon process owns SQLite write connections; repository calls do not expose connections across the crate boundary. The dependency lock pins one SQLite source identifier and build. Before SQLite initialization the process sets `SQLITE_CONFIG_STMTJRNL_SPILL` to `-1`; the pinned build must report compile option `TEMP_STORE=3`. Every connection then verifies `PRAGMA temp_store = MEMORY`, `foreign_keys = ON`, `journal_mode = WAL`, `synchronous = FULL`, `page_size = SQLITE_PAGE_BYTES`, `max_page_count = MAXIMUM_SQLITE_DATABASE_PAGES`, and the manifest busy timeout before use. Thus statement journals cannot spill and temporary databases, sorts, transient indexes, and materialized results use bounded memory. The repository and migrations use a closed, statically inventoried set of parameterized SQL statements; dynamic SQL, `ATTACH`, `DETACH`, `VACUUM`, `VACUUM INTO`, temporary-schema objects, caller-controlled pragmas, and every unaccounted temp-file-producing path are forbidden. Each statement has manifest-bounded inputs/results and an independently checked query plan; a new or changed statement cannot ship until the inventory, memory bound, and no-disk-transient oracle accept it. Every read transaction is internal, copies its bounded result before returning, and uses the pinned SQLite progress/interrupt boundary plus injected monotonic clock to end by `MAXIMUM_SQLITE_READ_TRANSACTION_MILLISECONDS`; `Wait` and response writes never retain a read transaction. Every write transaction precomputes and reserves its worst-case changed-page count and refuses before `BEGIN` when it exceeds `MAXIMUM_SQLITE_WRITE_TRANSACTION_PAGES`.

The daemon owns physical-file accounting and checkpoints. At the manifest passive-checkpoint write threshold it attempts a passive checkpoint and records returned log/checkpointed frame counts. Before another write can begin at or above `SQLITE_WRITE_BACKPRESSURE_BYTES`, admission and all fact-producing writes enter `PersistentStorageBackpressure`; after bounded readers drain, the daemon attempts a truncate checkpoint under `SQLITE_CHECKPOINT_RECOVERY_MILLISECONDS`. Success requires observed database, write-ahead-log, and shared-memory handle lengths to remain within their individual maxima. Busy, interrupted, failed, over-time, over-frame, or still-over-high-water recovery keeps writes refused without deleting state; read-only status and maintenance diagnosis remain available. Graceful stop and explicit maintenance use the same policy after stopping admission.

Every daemon connection selects the contract's restrictive delegating VFS over the exact pinned platform built-in local-filesystem VFS. For the active database it permits only the exact main database, `-wal`, and `-shm` objects; for atomic rebuild it additionally permits exactly one same-directory replacement main database. The disposable replacement is built exclusively under `journal_mode = OFF`, `locking_mode = EXCLUSIVE`, memory temp-store and statement-journal rules, then integrity-checked, closed, synchronized, and atomically installed; the VFS forbids a replacement journal, WAL, or shared-memory sidecar. It rejects every `SQLITE_OPEN_TEMP_DB`, `SQLITE_OPEN_TEMP_JOURNAL`, `SQLITE_OPEN_TRANSIENT_DB`, `SQLITE_OPEN_SUBJOURNAL`, `SQLITE_OPEN_SUPER_JOURNAL`, `SQLITE_OPEN_DELETEONCLOSE`, rollback-journal, master-journal, unknown sidecar, or outside-state-root open. `SQLITE_TMPDIR`, `TMPDIR`, `TEMP`, `TMP`, and platform ambient temporary roots are poisoned in conformance and cannot become SQLite authority. Startup verifies the pinned SQLite source/build options, configuration-before-initialization, built-in/VFS identity, closed SQL inventory, exact object whitelist, and no-spill invariants before mutation or readiness. If any fact cannot be verified, or any prohibited open is attempted, readiness fails unchanged. Startup then validates the whitelisted active files, replays/recover-checkpoints a valid committed WAL, and refuses readiness unchanged if any physical bound is violated. A client request cannot force or bypass a checkpoint. All whitelisted objects and their directory are current-user-only. Initial creation synchronizes the file and directory; accepted-operation acknowledgement occurs only after the `FULL` transaction commit returns; migrations and atomic replacement reserve `MAXIMUM_SQLITE_REPLACEMENT_PHYSICAL_BYTES` and synchronize in file-then-rename-then-directory order. No logical-row count is presented as a physical-file bound, and no unlisted disk transient exists outside the replacement formula.
