# Plan 0008 — FSM Workflow Integration

> Prove that the pinned FSM executor can invoke a Slingshot command through the standard-input/output Model Context Protocol server and drive a durable workflow outcome.

## Why this plan

The integration boundary is executable behavior, not a shared Rust dependency. The FSM executor starts one Model Context Protocol server process for one effect attempt, negotiates revision 2025-06-18, calls one fixed tool, and maps the result into a durable acknowledgement. Slingshot connects that short-lived protocol process to the target daemon. The daemon and author transport retain one durable logical operation and admit at most one fenced command-effect attempt; Sling may retain the transport-contract-bounded set of duplicate physical job records or at-least-once delivery attempts, and every attempt that loses the logical effect gate must no-op.

A compatibility claim based only on a hand-written client can miss handler-table validation, process lifetime, retry classification, acknowledgement mapping, and workflow transition behavior. This plan builds and runs the real FSM source pinned at commit 7d183e4d7a6b130343ea7d88897e0d029f604813 from https://github.com/koraytaylan/fsm. No test assumes a developer home directory or sibling checkout.

Each workflow store supplies the compatibility manifest's exact bounded nonsecret `workflow_operation_namespace` that remains stable for that store's lifetime. For each Plan 0007 registry command effect, the workflow derives `workflow_effect_operation_key` from that namespace, the exact-spelling bounded instance request identifier, and one unsigned intended command-effect occurrence through the closed canonical JSON/SHA-256/prefix contract, passes it as the command tool's `operation_key`, and keeps it stable across retries of that occurrence. The only suffixes are empty and compensation-only `-backup-restore`. Repeated command attempts therefore attach to the same daemon and author logical operation and effect gate, while two deliberate command occurrences or two independently namespaced stores use different keys and create different logical operations. Physical Sling record identity and count are never workflow identity. Plan 0007 maintenance preview/apply tool schemas and maintenance-result resource contracts reject operation keys and operation identifiers; exact target plus reviewed preview digest, durable application receipt, and target-qualified association lifecycle provide their independent replay contract. Resource readability first obtains target-and-identifier-only `MaintenanceResultMetadata`, then begins expected-digest `MaintenanceResultRead` only under byte-identical association facts or the sole checked current-preview-to-application-receipt owner/revision transition.

- **0033 — Workflow Outcomes.** Run development-owned real-process scenarios for successful commands, truthfully classified failed commands, post-success artifact recovery and result-unavailable evidence, explicit compensation gated first by verified remote-failure authority and then by a separate domain approval, disjoint target-qualified `structured_result_artifact_access` and operation-free `maintenance_result_access` outcomes whose `ack.result.structured` values remain exact objects, reserve `structured_result` solely for the deterministic operation artifact slot, prove keyless maintenance target/reviewed-digest receipt replay plus complete association/`MaintenanceResultMetadata`-then-read/replay/ownership/supersession/retirement evidence, and use per-command-occurrence provenance to prove one durable logical operation plus at most one fenced command-effect attempt while bounded duplicate physical Sling records no-op after losing the gate.
- **0034 — Retry, Restart, and Reference.** Prove the pinned FSM's handler timeout detaches and retries one namespaced durable logical operation without treating nonterminal state as failure or using physical-record cardinality as identity, prove daemon restart is transparent within the handler deadline and retains the same effect fence, keep present-state documentation aligned with the digest/executable/root-isolation/size contracts, and expose the closed committed Plan 0008 integration-target inventory as one provider-neutral repository-local compatibility gate against explicitly supplied pinned source and an optional manifest-bounded Cargo-home seed that forces frozen/offline mode. Plan 0009 alone may give that generic seed input verified release-cache provenance and adapt the gate to owner-confirmed hosted automation.

## Out of scope

- Modifications to the FSM repository or its journal, scheduler, executor, statechart, command-line, or Model Context Protocol implementation.
- Linking Slingshot against FSM crates.
- Java slingshot-agent implementation or live AEM semantics.
- Inferring registry-command idempotency from JSON-RPC request identifiers or an unavailable FSM internal effect identifier; the explicit workflow-supplied command operation key is authoritative only for that registry command occurrence and never supplies maintenance-control identity.
- Copying package bytes into an FSM acknowledgement or journal.
- Automatic rollback. Compensation is an explicit effect and transition in the fixture machine.
- Treating `isError`, `mcp_error`, or a handler's static `on_failed` event as proof of remote-failure authority.
