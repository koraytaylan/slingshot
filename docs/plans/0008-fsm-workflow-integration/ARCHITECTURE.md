# Plan 0008 — FSM Workflow Integration

## Architectural boundary

Slingshot and FSM share no compiled code. The compatibility boundary consists of:

- the pinned FSM source repository and commit;
- FSM handler table format fsm.handlers/1;
- Model Context Protocol revision 2025-06-18;
- Plan 0007 Slingshot tool names and schemas;
- the exact `slingshot.daemon-runtime-contract/1` and `slingshot.author-agent-transport-contract/1` sidecar digests;
- structured success and error result mapping;
- one bounded nonsecret `workflow_operation_namespace` stable for the workflow store plus one bounded `workflow_effect_operation_key` derived uniquely per intended Plan 0007 registry command-effect occurrence and held stable for its retries; and
- operation-free maintenance preview, apply, and result-resource controls whose exact target/reviewed-digest/receipt/association contracts contain no workflow operation identity.

The current FSM executor creates one Model Context Protocol child process per effect, performs `initialize`, sends `notifications/initialized`, calls the fixed tool directly, and maps the response into an acknowledgement. It does not issue `tools/list` in this path. Each handler has a literal rooted executable path, fixed tool name, argument template, timeout, retry policy, and optional success and failure events. A tool result with `isError: true` and a JSON-RPC error both map to the single `mcp_error` retry class. After an immediate failure or retry exhaustion, the executor emits the handler table's static `on_failed` event and static payload; it does not project the tool acknowledgement into that event. Timeout, spawn, protocol, and other unsuccessful handler outcomes can select the same static failure event. Consequently, `mcp_error` and `on_failed` express only handler failure and never establish remote-job authority.

The Slingshot protocol child owns no remote state. It connects to the already running target daemon for the handler's fixed profile and environment. For a registry command handler, closing or killing that child detaches one waiter and does not cancel the daemon operation, author-side durable logical operation, or fenced effect gate. For a maintenance control, child loss likewise cannot reinterpret a committed target/reviewed-digest application receipt or its retained associations as a workflow operation.

## 0034 — Retry, Restart, and Reference

The retry scenario configures a kind `mcp` handler with attempts greater than one and `retry.on = ["timeout"]`. FakeAuthor accepts the logical operation and delays terminal state past the first handler timeout. FSM terminates that protocol child, records `timeout`, and starts a later child with byte-identical arguments and the same store-namespaced operation key; the daemon attaches it to the existing daemon and author logical operation. FakeAuthor then completes that logical operation. The transport may retain bounded duplicate physical Sling records or delivery attempts, but only the winner of the already durable effect fence may attempt the command and every loser no-ops. A separate externally broken-child case pins its actual failure classification, configures that class as non-retryable, and proves child loss only detaches observation. A two-store case uses the same instance request identifier and occurrence under distinct stable namespaces and proves distinct operation keys, logical operations, and effect gates without asserting physical-record cardinality. Timeout exhaustion is indeterminate: it does not prove whether a mutation ran. No `on_failed` path directly emits compensation, regardless of the executor failure class.
