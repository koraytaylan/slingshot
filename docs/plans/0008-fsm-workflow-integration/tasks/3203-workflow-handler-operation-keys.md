# Workflow Handler Operation Keys

Validate a real fsm.handlers/1 table in which each fixed Plan 0007 registry command tool consumes one store-namespaced stable key per intended command-effect occurrence while operation-free maintenance controls reject command-operation identity.

**Steps:**

1. Commit the handler template, independent canonical-preimage/digest/suffix vectors, both exact upstream contract provenance identities, command-versus-maintenance classification vectors, surplus maintenance-control operation-key refusals, and operation-key fixture machines containing one stable workflow-store namespace, two intended occurrences of the same command handler plus a retry, and two independent stores with equal instance request identifiers but distinct namespaces before writing the expansion and validation test.
2. Define kind mcp handlers with the absolute `slingshot-development` process-child executable placeholder only at argv position zero, fixed development-only private-root/sentinel arguments and `model-context-protocol` role, the unchanged Plan 0007 standard-input/output server arguments for one fixed profile/environment after `--`, and fixed tool names. Registry command handlers use exact Plan 0003 wire names; maintenance handlers use only Plan 0007's fixed `maintenance_preview` or `maintenance_apply` control name. No machine value may select either root, role, executable, profile, environment, or tool.
3. Consume `compatibility/finite-state-machine.toml` as the sole key-contract authority for registry command effects. Require nonempty exact-spelling valid-UTF-8 `workflow_operation_namespace` and `instance_request_identifier` strings of at most 128 bytes with U+0000–U+001F and U+007F–U+009F excluded, and an `occurrence` unsigned integer in `0..=18_446_744_073_709_551_615` assigned once per intended registry command-effect occurrence. Serialize exactly one no-whitespace/no-newline JSON object in byte-lexicographic member order `format`, `instance_request_identifier`, `occurrence`, `workflow_operation_namespace`, with literal format `slingshot.workflow-effect-operation-key/1`, direct Unicode except required quote/reverse-solidus escapes, and minimal-base-ten occurrence. Hash those complete UTF-8 bytes with SHA-256 and form the exact 92-byte base key from `slingshot-workflow-effect-1-` plus 64 lowercase hexadecimal characters. Retain the daemon-runtime/author-transport identities as separate workflow provenance; never add either digest to this fixed preimage, reinterpret a stored key after drift, or use the key as proof of a physical Sling record or maintenance receipt.
4. Pass that base key losslessly as `operation_key` for every registry command effect. Permit only the manifest's empty suffix and literal `-backup-restore`, with exact suffix/final-key bounds 15/107 bytes; only the explicitly approved compensation command effect may use `-backup-restore`. Reject every other spelling instead of accepting an arbitrary bounded suffix. Require maintenance preview/apply handler input schemas to reject `operation_key`, `workflow_effect_operation_key`, an occurrence, and every operation/artifact identity. Maintenance preview uses its exact target and bounded selection criteria; maintenance apply uses the exact target plus reviewed preview digest, and an exact repeated call resolves its durable applied/replayed receipt and associations without a workflow operation key. A maintenance-result resource reference remains target/association-qualified and accepts no operation-key component; its read first obtains target-and-identifier-only `MaintenanceResultMetadata`, then supplies the returned content digest to `MaintenanceResultRead` under the exact unchanged-or-checked-ownership-transfer lookup-to-start rule.
5. Configure named finite handler-timeout values and complete explicit retry objects, including the one-attempt no-retry cases; give every present advance explicit payload and stamps, use `timeout` only where the scenario explicitly admits retry, and treat every `mcp_error`/`on_failed` transition as a generic handler failure that cannot directly claim remote authority or emit compensation. A maintenance-apply timeout retry repeats byte-identical target and reviewed-digest arguments and accepts only exact durable receipt replay.
6. Expand the executable placeholder in an isolated file and invoke the shared Slingshot compatibility validator, which gives the exact real JSON check invocation its own explicit empty data directory plus sanitized private home/configuration environment, independently proves the expanded executable is an accessible regular file, then compares the fields that command exposes with the retry and complete advance fields projected from the same already-accepted source table. The validator first classifies the fixed Plan 0007 tool: it requires and validates the manifest-derived key only for registry command handlers, rejects that key and operation identity for maintenance controls/resources, and validates the latter's target/reviewed-digest/receipt-association contract separately.

**Tests:**

- The real FSM accepts the expanded table as fsm.handlers/1 and the Slingshot validator accepts its fixed tools, arguments, complete retry objects, and explicit advance payload/stamps without inferring a source-only default.
- argv position zero is absolute and literal; no machine value can change the executable or tool name.
- Every registry command handler requires the manifest-bounded namespace, instance request identifier, occurrence, and exact 92-byte base key; two intended same-handler command occurrences receive distinct values while a retry receives the original value. Maintenance preview/apply handlers reject all four values and any `operation_key` member.
- Equal instance request identifiers and occurrences in distinct store namespaces produce distinct operation keys and daemon/author logical operations, while restarting one store preserves its namespace and exact key; physical Sling record sets are not identity.
- Re-expanding one occurrence key produces byte-identical canonical preimage, digest, key, and tool arguments. Empty/exact/next-byte strings, occurrence zero/maximum/overflow, disallowed controls, composed/decomposed Unicode, member order, required escaping, minimal integer spelling, base-key case/length, empty/`-backup-restore` suffixes, unknown/over-bound/wrong-handler suffixes, and independent upstream-contract drift match the manifest vectors and prove contract provenance never mutates or aliases the key.
- FSM preflight rejects its malformed handler cases; the Slingshot validator separately rejects a missing registry-command workflow-effect key, a surplus maintenance operation key or operation/artifact identity, a maintenance apply without exact target/reviewed digest, registry-unknown tools, malformed argument templates, suffix/timeout bound violations, unsupported wait arguments, invalid retry classes, incomplete retry objects, omitted advance fields, and check-output/source mismatches before a workflow starts.
- Handler fixtures use authority-neutral `on_failed` events; no static failure payload claims a terminal disposition or remote authority.
- Exact maintenance apply retry reuses target/reviewed digest and returns the same durable receipt/associations; changed target/digest conflicts and no test derives maintenance replay from the command-key preimage.
