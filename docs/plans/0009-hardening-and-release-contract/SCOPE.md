# Plan 0009 — Hardening and Release Contract

> Turn the completed product surface into release evidence that survives hostile bytes, process death, network loss, storage failure, credential attacks, compatibility checks, and optional contact with a real author.

## Why this plan

Plans 0001 through 0008 prove their features at the task boundary. A release claim is broader: every parser remains bounded under arbitrary input, durable invariants survive combinations of failures, credentials remain absent from every unintended observable surface, the locked dependency graph still compiles at the declared minimum Rust version, compatibility changes require an explicit version or migration, and packaged binaries reproduce the behavior that the documentation states.

This plan supplements the earlier suites rather than replacing them. It reuses the same product APIs, fake identity service, fake author, local endpoints, operation store, command-line adapter, Model Context Protocol server, and workflow integration under stronger generative and failure-driven tests. An optional live harness can verify read-only behavior against an operator-selected Adobe Experience Manager author, but normal automation remains hermetic and no live test connects to a publisher.

Makina task dependencies are bundle-local. Plan 0009 therefore becomes eligible only through the root sequential Phase R contract: Plans 0001–0008 must all be successfully integrated and Plan 0009's validation-base OID must equal Plan 0008's verified final-integration OID exactly. That base supplies every earlier feature, Plan 0008's repository-local gate, and its `docs/WORKFLOWS.md`; no Plan 0009 frontmatter names a cross-bundle task or assumes numeric order grants readiness.

## Out of scope

The Java `slingshot-agent` implementation, automatic mutation of a live Adobe Experience Manager environment, direct publisher connections, external penetration certification, hosted release publication, end-user executable/package signing, private signing-key custody, and service-level performance guarantees are outside this plan. GitHub's keyless build-provenance attestation is in scope solely to authenticate native evidence transferred to offline verification. Hermetic agent conformance proves the language-neutral boundary rather than compatibility with every separately installed bundle or Adobe Experience Manager patch level. Fuzzing and chaos establish the named invariants for exercised inputs and checkpoints; they do not claim the absence of every possible defect.

Automation provider/repository identity, exact native runner mappings, each row's source-protection claim and network-denial primitive, the release-acceptance coordinator row/container authority, the single probed FSM-compatible row, native-evidence trust, and license choice are owner decisions rather than inferred plan values. Until the three gated authority/legal tasks receive them, implementation may complete through non-release product evidence but no native workflow, release-input cache, archive, cache-isolated acceptance, or release task is ready. A digest-observation-only native row may support reproducibility evidence, but it cannot be described as immutable or resistant to a malicious same-principal compiler/build script.
