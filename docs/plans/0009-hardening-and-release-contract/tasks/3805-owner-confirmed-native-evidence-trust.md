# Owner-Confirmed Native Evidence Trust

Offline native evidence becomes authority only through an owner-approved signer, identity policy, and trust root. Internal checksums alone prove consistency and never prove where a build or smoke run occurred.

**Steps:**

1. Keep this task gated until the repository owner confirms GitHub Artifact Attestations as the native-evidence authority, confirms either a public GitHub repository or an eligible private/internal GitHub Enterprise Cloud repository rather than GitHub Enterprise Server, and approves the exact public/private Sigstore issuer, owner/repository identifiers, release workflow identity, GitHub-hosted runner class constraints, in-toto statement and SLSA provenance versions, offline verification tool/version, and reviewed official trusted-root snapshot.
2. Commit accepted and rejected policy, root, bundle, statement, subject, predicate, identity, expiry, and rotation fixtures before implementation. Use an independently pinned provider-signed cryptographic fixture and its own exact fixture identity/root rather than recording output generated by the verifier under test or claiming it came from Slingshot's not-yet-created release workflow.
3. Define closed `support/release-attestation-policy.toml` data with repository visibility/eligibility, immutable owner/repository identifiers from Plan 0001, exact release workflow path, issuer and builder identity constraints, permitted hosted runner classes, statement/predicate versions, digest algorithms, verifier identity/version, trusted-root path/digest/provenance, and certificate/integrated-time validity policy. Store no signing key, token, certificate private material, ambient default branch, or mutable repository display name as authority.
4. Commit the reviewed provider trusted-root snapshot and verify its declared digest before parsing a bundle. The policy accepts no operating-system trust store, network lookup, ambient Git remote, verifier default root, or unpinned root update.
5. Select the exact offline-capable GitHub CLI version only after approval, add its install provenance/checksum to `support/repository-tools.toml` and its version check to `scripts/quality`, and implement a development validator that first authenticates a bundle offline with the pinned verifier/root and then requires the policy-supplied issuer, immutable repository/owner, release workflow, source revision, builder/hosted-runner class, statement/predicate versions, and complete subject set. Unit fixtures prove the cryptographic/identity mechanism under their independent fixture authority; task `release-artifact-contract` owns the first live exact-Slingshot-workflow bundle proof. Verification failure makes every embedded manifest assertion untrusted.
6. Add an explicit nonmutating root-review command that verifies a separately named provider candidate and its provenance and emits proposed policy/root bytes. Expected provider key rotation requires a reviewed committed update before a later source revision can build; issuer, repository/workflow identity, visibility/eligibility, predicate-version, or runner-class changes re-enter this owner gate. Release verification never fetches, repairs, or advances trust material and documentation states that an offline snapshot cannot reveal a provider revocation published after that snapshot.

**Tests:**

- The independently pinned provider fixture authenticates under its exact fixture policy/root offline, while the owner-approved Slingshot policy passes closed structural validation without claiming a release-workflow signature exists yet.
- Unsigned, malformed, expired, wrong-root, wrong-issuer, wrong-owner/repository, wrong-workflow, wrong-source, self-hosted, cross-target, wrong-predicate, missing-subject, extra-subject, digest-mismatched, and replayed-for-another-revision bundles fail before evidence parsing.
- A self-consistent archive and manifest without a valid bundle remain untrusted and cannot satisfy one native row.
- Policy/root mutation, verifier-version drift, unsupported private/Enterprise Server hosting, a default verifier root, or a network attempt fails with bounded non-secret diagnostics; root-review output never mutates the repository or candidate.

- **Done when:** `cargo test -p slingshot-development --test release_attestation_policy` proves the pinned verifier authenticates the independent GitHub-hosted fixture offline, the owner-confirmed Slingshot signer/root/identity policy is closed and valid, and every unsigned, self-asserted, mismatched, ambient-trust, or cross-revision fixture is rejected without claiming a live Slingshot bundle before task `release-artifact-contract`.
