# Plan 0009 — Hardening and Release Contract

> Supplemental evidence and the release boundary over the complete Slingshot workspace.

## Implementer orientation

1. Every product capability already has an owning plan and focused tests. Tasks here reuse public seams and add only the smallest failure-injection or development support required to make a release claim falsifiable.
2. Fuzz corpora, compatibility snapshots, threat sentinels, and chaos seeds are committed before their harnesses. Expected data comes from the documented contract, not from recording the implementation under test.
3. All normal tests are hermetic. The live Adobe Experience Manager harness is disabled unless explicitly selected and can dispatch only registry-classified read-only commands.
4. Failure tests use temporary runtime, configuration, database, artifact, and certificate roots. They never alter the real user configuration directory or contact an unlisted address.
5. Every chaos failure prints its seed, checkpoint, target, and operation identifier and accepts a named environment override for deeper runs. Committed defaults are measured against the shared continuous-integration budget.
6. Rust declarations and repository paths use unabbreviated local words. Semantic domain and operational numeric values use named constants; intrinsic identity, indexing, protocol-structural syntax, and parsed fixture or version grammar retain their conventional literals. Every Rust file remains at or below 1,000 physical lines, and functions stay within the repository complexity ceiling.
7. Rust documentation and product Markdown state present behavior only. `docs/plans/**` remains structurally excluded from the temporal documentation policy because planning prose is intentionally prospective.
8. A hardening test that exposes a product defect may modify only the exact owning source files named by its task footprint; it must retain the regression that made the defect visible.
9. Makina resolves task dependencies only inside this directory. Plan 0009 receives Plans 0001–0008 solely through the sequential Phase R rule: all eight are complete and this plan's validation-base OID equals Plan 0008's verified final-integration OID before any Plan 0009 task is ready. No numeric-order assumption or cross-bundle task identifier appears in frontmatter.
