# Plan 0006 — Command-Line Experience

> The parser, catalog bindings, operation observation, rendering, and process proofs.

## Implementer orientation

The command-line crate is a local-protocol client, never an Adobe Experience Manager client. Arguments become shared registry requests before crossing the daemon boundary. Rust declarations use complete words such as `CommandInvocation`, `SelectedEnvironment`, `SelectedEnvironmentRevision`, `OperationIdentifier`, `ArtifactIdentifier`, `MachineOutcomeEnvelope`, and `OpenServiceGatewayInitiativeConfigurationCommand`. User-facing standardized spellings such as `json` remain wire values, not shortened Rust names. Every exit value, readiness deadline, message bound, pagination bound, staging-file mode, and terminal width fallback has a named constant. Parsers, validation, configuration checking, daemon discovery, transport, rendering, application dispatch, and process control stay in separate modules, no source file exceeds 1000 lines, and each task starts with fixtures that prove its stated claim. Task 2505 adopts Plan 0001's crate and command-family roots, declares the complete Plan 0006 leaf inventory once, and creates compiling documentation-only leaves before any behavioral task; every later task implements an already crate-reachable module without reopening a shared parent merely to expose it.

## 0025 — Invocation and Daemon Selection

`CommandInvocation` is a closed tree with leaf-scoped profile/environment selection, output mode, detachment, and caller operation key values. Parsing performs no filesystem, process, daemon, or network work. Registry-aware validation requires a caller-supplied key for all five descriptors not classified intrinsically idempotent, including read-classified `load_content_as_json`; only the seven intrinsically idempotent configuration/discovery reads may omit it. Output mode applies only to ordinary rendered leaves, while detachment and operation key apply only to registry submissions. Plan 0007's `model-context-protocol serve` leaf accepts profile/environment selection only and rejects output, detachment, operation-key, and ordinary target-override fields. Help and version are the only leaves completed from immutable command metadata. Configuration check has an explicit application service that resolves the selection through Plan 0002, opens every referenced local input through the safe configuration file reader, validates Basic credentials or Cloud credential JSON and private key, validates additional certificate authority files and `SelectedEnvironmentRevision`, and returns without creating a daemon connector, starting a process, or making a network request. Its public failure rendering consumes Plan 0002's closed `ConfigurationDiagnostic` unchanged: only `source_class`, `stage`, manifest-vocabulary `structural_location`, `code`, and `occurrences`, under the upstream inclusive 32-item truncation-marker rule. It emits no source path, profile/environment/credential/certificate reference or name, digest, source-order oracle, value, or remediation suggestion.

Operation, observation, listing, maintenance, and explicit daemon-start leaves use Plan 0002's complete `SelectedEnvironment`, its nonsecret `AuthorTargetIdentity`, and its `SelectedEnvironmentRevision`; daemon status, ping, and stop resolve only the explicit pair or complete default pair into validated `ProfileName` and `EnvironmentName`. Both paths create the same name-only canonical namespace key, so an invalid or changed profile document cannot prevent an operator from stopping its existing owner.

Every daemon-backed execution request and readiness handshake carries the current author target identity, selected-environment revision, and the exact digest of canonical `policy/daemon-runtime-contract-1.json`, format `slingshot.daemon-runtime-contract/1`. The client recomputes `DaemonRuntimeContractDigest` from exact repository/embedded bytes and sidecar, compares it with `Hello`, and sends it as the expected value on every versioned operation request. A runtime-digest mismatch refuses operation/list/maintenance access before repository or executor use; retained `daemon.ping`, status, and exact-current-nonce `daemon.stop` remain usable to diagnose or stop the incompatible owner and never pretend compatibility. A live endpoint whose immutable target or loaded revision differs is likewise not used and is not silently replaced; the diagnostic names both nonsecret revisions and directs the operator to stop and start that namespace. Operation and explicit start first attempt the namespace's authenticated local endpoint. A missing endpoint invokes the current executable's internal daemon entry point with explicit profile and environment names, detached standard streams, a namespace lock, and no shell. Concurrent starters race on the daemon lock rather than creating multiple processes. The client waits for a bounded protocol readiness exchange, detects early child exit, and reconnects through the normal local client. Daemon status, ping, and stop probe only an existing namespace and never cause a spawn. Stop sends the nonce-bound local request, waits for bounded ownership release, and makes no remote cancellation. An existing incompatible or unhealthy endpoint fails with its own exit class.

`CommandLineApplication` composes the parser, target selector, configuration checker, daemon lifecycle, operation services, renderers, and exit classifier. One exhaustive dispatch over `CommandInvocation` proves every parser leaf reaches exactly one service and one final rendering path. The library entry accepts injected boundaries; the binary entry supplies production boundaries and maps the returned exit classification to the process exit.

## 0026 — Command Catalog

Each command module maps parsed values to exactly one operation descriptor from the registry delivered by Plan 0003. The binding consumes the descriptor's stable wire name, exact command semantic version `1.0.0`, exact canonical `slingshot.command-contract-limits/1` digest, separate argument/result schema digests, mutation classification, and failure inventory; the command-line crate declares none of those values independently. Application construction rejects a missing descriptor, any version other than the registry/limits-manifest value, a limits-digest or role-digest disagreement, an unsupported schema type, an unbound command, or an extra command before parsing can reach daemon access. The command layer adds spelling, positional/option rules, and help text only. Task 2505 alone declares the exact ordered `commands/mod.rs` inventory `content`, `package`, `replication`, `configuration`, `page_query`, `path_query`, `asset_query`, `page_mutation`; the five catalog tasks implement only their disjoint already-declared leaf files, and final composition task 2706 wires the compiled leaves without reopening the parent. A compile-time catalog coverage table and snapshot test fail when a registry operation lacks a command, a command names no registry operation, or the shared root has a missing/duplicate/reordered/orphan declaration.

Schema consumption also authenticates Plan 0003's separate byte contract rather than treating a matching five-field descriptor as sufficient by itself. The command catalog loads exact canonical `schemas/command-canonical-json-1.json`, requires format `slingshot.command-canonical-json/1`, recomputes its SHA-256 digest, requires the command-schema manifest's canonical-contract digest and each argument/result root's exact `x-slingshot-canonical-json-contract-sha256` annotation to equal that digest, recomputes each annotated role-schema digest, and only then compares the unchanged five-field compatibility identity. The canonical-contract digest remains schema provenance bound inside both role bytes; it is not a sixth field in `SelectedCommandContractIdentity`. Every serialized command-role document is checked in one fixed order without parse-and-reserialize repair: the language-neutral raw-byte validator and its per-role ordered-array inventory first, the ordinary Draft 2020-12 decoded shape second, and the typed/cross-field constructor third. CLI values are serialized canonically and must pass that same pipeline before submission; raw property/predicate inputs and canonical command results cannot bypass its first stage. Contract-artifact, manifest, annotation, argument-role, and result-role drift are independently fail-closed before daemon access.

The client also consumes exact canonical `policy/author-agent-transport-contract-1.json`, format `slingshot.author-agent-transport-contract/1`, and recomputes `AuthorAgentTransportContractDigest` from its repository/embedded bytes and sidecar. For any current agent-backed operation receipt, status, result, failure, artifact fact, or maintenance child effect presented as compatible, the daemon-supplied persisted transport digest must equal that exact value before command-schema validation or rendering. A missing or different digest is an explicit provenance incompatibility, never a compatible command outcome. Historical metadata under an older digest may remain bounded read-only maintenance/list evidence exactly as supplied by the daemon, but the client does not relabel it as current, reinterpret its command bytes, or execute/recover through the current transport contract.

Content commands load a repository path as the registry's JSON representation with its optional depth and request shallow or recursive replication. Package download carries its bounded package name, one or more roots, and ordered include and exclude pattern lists without interpreting those patterns locally. Configuration inspection accepts the persistent identifier for an Open Service Gateway Initiative configuration and performs a read operation.

Query commands construct the shared structured query from a required root, an optional node type, and repeated `--property-predicate <canonical-json-object>` options; no free-form or raw query grammar is accepted. The accepted field names and discriminator/type tags are exactly the committed Plan 0003 canonical schema and examples, not a parallel command-line encoding. Every object has `property_path` plus one `operator`: `exists` has no value; `equals` and `not_equals` have one PropertyValue named `value`; `scalar_in`, `list_contains_any`, and `list_contains_all` have non-empty ordered-unique homogeneous scalar `values`; `less_than`, `less_than_or_equal`, `greater_than`, and `greater_than_or_equal` have one ordered scalar `value`.

A scalar is exactly `{"type":<type-tag>,"value":...}`, where `type-tag` is one of `"string"`, `"boolean"`, `"integer"`, `"decimal"`, `"date_time"`, or `"repository_path"`; signed 64-bit integers use canonical base-ten strings. A PropertyValue is `{"cardinality":"single","value":<scalar>}` or `{"cardinality":"multiple","values":[<scalar>,...]}`; multiple values are non-empty and share one type. Ordered comparisons accept strings, integers, decimals, and date-time values and reject booleans, repository paths, and lists. Unknown/surplus fields, wrong operator arity, untagged values, noncanonical decimal/date-time/integer encodings, and heterogeneous lists fail before daemon access.

Page queries carry the required root plus phrase, template, or a non-empty component set with explicit any-or-all matching. The phrase argument is passed directly to Plan 0003's SearchPhrase constructor: the CLI never trims or normalizes it, preserves every accepted UTF-8 byte and internal whitespace scalar, and reports leading/trailing Unicode 15.1 White_Space as noncanonical. Asset metadata queries carry the required root, media formats, byte bounds, repeated tags with explicit any-or-all matching, and property predicates; referenced-asset queries carry the page path. Each asset byte-bound flag accepts only the canonical unsigned base-ten spelling `0|[1-9][0-9]*`, converts with checked arithmetic into Plan 0003 `AssetByteLength` over `0..=9_223_372_036_854_775_807`, and validates an inverted range only after both endpoints are valid; plus, leading zero, minus, fraction, exponent, next-integer, and parser-overflow spellings fail before daemon access. The typed CLI constructor rejects duplicate media-format or tag flags and sorts each accepted set once in ascending UTF-8 bytes, so invocation permutations produce one canonical signed request. Package include/exclude lists and repeated property predicates remain ordered sequences and are never sorted as sets.

Every command-discovery leaf exposes `--offset` and `--limit`, or one opaque `--continuation-token`. The token is mutually exclusive with either result-window option, is validated only for Plan 0003's exact MAXIMUM_CONTINUATION_TOKEN_BYTES manifest bound and control-free/nonempty opaque spelling, and is passed byte-for-byte without decoding, trimming, normalization, logging, or synthesis. Operation-list continuation is the separate Plan 0004 type and is not silently accepted as a command continuation token. Page creation carries parent, name, title, template, and optional property document; component addition carries page, relative parent resource, component name, resource type, and optional property document. Property files are bounded JSON objects read before submission, reject duplicate keys, and are never treated as shell or template text.

All path-like values use the shared repository-path type. Recursive, package, query, page, and component requests are visibly classified as reads or mutations in help and machine output. No command accepts a tier flag, base address, credential, or publisher override.

The renderer and exit layer consume the semantic-versioned structured-failure object carried by the authenticated operation result; they never translate it into a CLI-owned alias, discard its permitted detail field, or reconstruct it from prose. The revised exact inventory includes all five content-free continuation-token failures; configuration lookup, unsupported-value, malformed-value, value-budget, and result-budget failures with only their registered `reason` or `budget`; FileVault profile/filter, pattern, anchor, construction, cleanup, publication, and eight-way evaluation-budget failures; and add-component's eight authoritative-no-effect categories including `parent_not_orderable` plus `mutation_outcome_unknown`. Machine mode embeds the exact validated closed object. Human mode prints its exact failure literal and every registered field, with no hidden key/value/filter/package bytes. Unknown categories, aliases, missing fields, surplus fields, wrong reason/budget literals, or a failure not registered for command version `1.0.0` are invariant failures rather than lossy fallbacks.

The synchronized failure shapes are exact. `continuation_token_malformed|continuation_token_integrity_invalid|continuation_token_wrong_target|continuation_token_wrong_query|continuation_token_expired`, `configuration_lookup_failed|configuration_lookup_mismatch|configuration_lookup_ambiguous`, and `filevault_profile_unsupported|filevault_filter_unrepresentable|repository_read_failed|filevault_package_failed|staging_cleanup_failed|artifact_publication_failed|artifact_publication_outcome_unknown` contain only `failure`. `configuration_lookup_budget_exceeded` adds only `budget: lookup_duration|matching_configurations`; `configuration_value_unsupported` adds only `reason: non_primary_type|non_unicode_value`; `configuration_value_malformed` adds only `reason: invalid_property_key|duplicate_property_key|null_value|mixed_types|nested_container|carrier_type_mismatch|empty_collection_type_unavailable`; `configuration_value_budget_exceeded` adds only `budget: scalar_string_bytes|sequence_items|sequence_canonical_bytes`; and `configuration_result_budget_exceeded` adds only `budget: property_count|serialized_result_bytes`. Package `pattern_rejected` adds only `collection: inclusion|exclusion` and zero-based `expression_index`; `root_not_found|root_access_denied` add only `root_path`; `evaluation_budget_exceeded` adds only `budget: candidate_paths|pattern_evaluations|selected_paths|filter_document_bytes|package_manifest_bytes|archive_entries|uncompressed_input_bytes|package_output_bytes`. Add-component `page_not_found|page_invalid|parent_not_found|parent_access_denied|parent_not_orderable|target_already_exists|property_rejected|repository_commit_failed|mutation_outcome_unknown` add only computed `target_path`.

## 0027 — Operation Observation

Submission first checks the registry's intrinsic-idempotency classification. A non-intrinsically-idempotent operation without a caller key fails before daemon access. With a supplied key, that value becomes the local operation identifier across process restarts. Only an intrinsically idempotent operation may omit the key; an injected identifier generator then creates it exactly once before the first local request and in-process reconnect paths retain it. Every execution request includes the current `AuthorTargetIdentity` and `SelectedEnvironmentRevision` checked during the readiness exchange; no execution command accepts a target digest override. Submission then returns a durable operation receipt. Without `--detach`, the client subscribes through the local protocol, renders progress to standard error, and waits for a terminal state before fetching the typed result. With `--detach`, it prints the receipt and exits successfully after durable daemon acceptance.

`operation status` renders the latest state without waiting; `wait` follows current-target progress; `result` retrieves the terminal structured result; explicit `operation resume` sends Plan 0004's `ResumeOperationRecovery` with the caller's required `--expected-revision` and `--expected-recovery-category`; and bounded `operation list` consumes Plan 0004's paginated operation service. Every `RecoveryRequired` status preserves exactly one `RecoveryExecutionEvidence` branch: `ExecutionCertainty(OperationExecutionCertainty)` for execution/reconciliation uncertainty, or fieldless `AuthoritativeRemoteSuccess` after the remote command has succeeded and only required result or artifact acquisition remains. Post-success `PersistentCapacityUnavailable` uses `AuthoritativeRemoteSuccess` and structurally carries no operation-certainty value. A fresh resume is legal only for the current target's manually resumable `RecoveryRequired` fact. It compares both observed preconditions, rejects active, historical, stale-revision, or changed-category fresh requests without scheduling, and returns the newly revised nonterminal envelope after one durable recovery schedule. An exact repeat first resolves Plan 0004's durable source receipt and returns that applied revision plus truthful current status with no second schedule even after later progress, another recovery cycle, terminal settlement, or daemon restart; maintenance of the owning terminal operation ends that replay lifetime. List, status, result, operation artifact, maintenance preview/apply, and maintenance result default to the current author-target partition and may accept a validated `--author-target-identity-digest` for a historical terminal partition. Every row/outcome includes that digest, so reused operation or maintenance-result identifiers cannot be confused across target changes. Wait, resume, and all execution/mutation commands reject the override, and historical nonterminal operation access is refused.

`maintenance preview` requires `--before` plus a bounded operation item limit and selects exactly one current or historical target partition. The cutoff applies to terminal settlement and completed prior application-receipt commit times respectively; Plan 0004 independently bounds deterministic completed-receipt retirement. The logical result is Plan 0004's complete canonical manifest: normalized criteria; every selected operation/revision and child-row effect including exact historical `AuthorAgentTransportContractDigest` provenance; every resume/application receipt effect; each artifact association/blob retain/delete decision; and exact before/projected/released capacity facts. The reviewed digest covers those complete canonical bytes. `maintenance apply` accepts only that preview digest plus the same selected partition; it accepts no fresh selection criteria. A fresh apply requires the reviewed facts to remain current. An exact target/digest repeat returns a completed durable receipt or resumes only its database-applied unreferenced-blob cleanup before returning exact actual effects, even after operation rows are absent or the daemon restarts. Wrong-partition, unknown, tampered, or stale digests refuse without mutation.

Neither preview nor applied/replayed output is truncated to fit the machine envelope. A complete canonical maintenance value that fits the inline logical-result budget uses its ordinary maintenance branch. One above that budget is installed by the daemon as canonical `application/json` under Plan 0004's operation-free target-qualified `MaintenanceResultIdentifier`; the association records preview/application kind, reviewed source digest, content digest, exact length, fixed media type, revision, and retention owner. Human and JSON output expose the same verified access entry and exact URI `slingshot://profiles/{profile}/environments/{environment}/targets/{author_target_identity_digest}/maintenance/results/{maintenance_result_identifier}`. `maintenance result <maintenance-result-identifier> --expected-digest <digest> --destination <path>` first calls target-and-identifier-only `MaintenanceResultMetadata`, requires the caller-supplied expected digest to equal the returned content digest, then calls `MaintenanceResultRead` with that digest. It requires read start to repeat every identity-bound metadata field and accepts only unchanged owner/revision or the checked current-preview-to-application-receipt transition; it never derives the digest from the identifier. The command uses the same locked no-follow staging/publication receipt boundary as operation artifacts without inventing an operation or slot, and refuses a missing, superseded, retired, target-mismatched, content-mismatched, or other metadata-changed association before publication. A lifecycle transaction ordered after atomic read start does not change the authenticated same-handle stream snapshot. Preview/apply replay and restart preserve the same URI/bytes; explicit supersession or completed-receipt retirement before a later read start makes exactly the former association unreadable. Plan 0007 reuses the identical identity/digest and lookup-to-start rule. The local readiness handshake still carries the current `AuthorTargetIdentity`, `SelectedEnvironmentRevision`, and `DaemonRuntimeContractDigest`, so selecting retained terminal history never impersonates the daemon's current target or bypasses stale-daemon refusal.

`operation artifact` addresses one `artifact_identifier` and reads bounded immutable chunks from the daemon. The downloader derives deterministic same-directory staging, sidecar, and lock names from the target-qualified operation and artifact identities. It acquires an exclusive cross-platform lock before opening or inspecting stage state and holds ownership from identity validation through final output commit. A second saver fails without reading or writing either stage file. Once locked, the downloader opens stage and sidecar without following links as current-user-only regular files and retains the opened handles throughout validation and resume. The sidecar canonically records target profile/environment, `author_target_identity_digest`, selected-environment revision, operation identifier, artifact identifier, expected digest, expected length, verified staging length, and a closed transfer/ready-to-publish/published-receipt state. Stale unlocked transfer state resumes only when those facts and the same-handle file length agree.

Completion verifies length and digest, synchronizes the staging handle and containing directory as required, and synchronizes the exact ready-to-publish receipt before attempting the non-overwriting atomic publication. Successful publication is the artifact command's success linearization point. If an interrupt wins before that publication commit, no new destination is published, the exact `artifact_transfer_interrupted` outcome wins, and the private self-consistent staging pair remains resumable. If publication wins, the destination is already the verified success and no signal at or after that point may select transfer interruption, tell the caller to resume, or attempt a second publication. The downloader retains the lock and exact receipt through final output acknowledgement, records published state when possible, and removes private receipt/staging metadata only after the complete success rendering commits. If process or output loss occurs after publication but before that rendering commit, an identical rerun under the same lock accepts only the exact ready/published receipt plus a no-follow same-handle regular destination whose length and digest match every recorded identity; it performs no download or publication and re-renders the original success. Any missing/mismatched receipt or destination fact remains an ordinary non-overwriting collision and preserves the destination. Tests include the crash gap between publication and published-state synchronization, so receipt recovery never depends on a second atomic filesystem mutation.

Human mode prints only the final successful receipt, result, or artifact location to standard output; progress and human-readable failures use standard error. JSON mode writes exactly one canonical, versioned `MachineOutcomeEnvelope` to standard output for success and failure. The shared envelope contains target profile/environment, nonsecret `author_target_identity_digest`, local operation identifier and state when present, and exactly one closed `outcome_type` branch:

- `operation_receipt`, containing durable `accepted` or `replayed` admission and current revision;
- `operation_status`, containing current lifecycle/revision plus bounded progress and recovery facts, with every `RecoveryRequired` fact carrying exactly one `RecoveryExecutionEvidence` branch and no cross-branch certainty;
- `inline_command_result`, containing one terminal schema-validated logical result;
- `command_artifact_access`, containing one schema-derived command-specific artifact result in which each `ArtifactDescriptor` leaf is replaced by a bounded access entry while every non-artifact result member is preserved exactly;
- `structured_result_artifact_access`, containing the daemon-created canonical JSON operation-artifact access entry;
- `operation_list_page`, containing a bounded page and opaque continuation token;
- `maintenance_preview`, containing a complete canonical effect/capacity manifest and digest only when it fits inline, or `maintenance_applied`, containing the exact target-qualified applied/replayed receipt and recorded effect/capacity summary only when it fits inline; either complete logical value otherwise uses `maintenance_result_access`, containing target digest, `MaintenanceResultIdentifier`, preview/application kind, reviewed source digest, content digest, exact length, fixed `application/json`, association revision, retention-owner class, and the exact operation-free maintenance URI;
- `configuration_check_report` or `daemon_control_result`, containing their bounded nonsecret control output;
- `operation_terminal_error`, preserving Plan 0004's conditional union and the complete validated Plan 0003 semantic failure object when present: authoritative nonexecution with `ConfirmedNotExecuted`; authoritative remote failure with no certainty field; fail-closed indeterminate with one unknown certainty; or fieldless authoritative remote success, which requires and is required by `ResultUnavailable` after proven remote success when the required result or artifact cannot be obtained or validated;
- `operation_control_error`, representing revision, state, or availability refusal without terminal-disposition fields; or
- `local_application_error`, representing an application failure that likewise cannot carry an operation-terminal disposition or certainty claim. Its interruption subvariants are closed: `submission_interrupted_before_receipt` carries only `error`, literal `admission: "unknown"`, and `retry_operation_identifier`; `operation_observation_interrupted` carries only `error`, `admission: "accepted|replayed"`, and `accepted_revision` alongside the envelope's known durable operation identifier; `artifact_transfer_interrupted` carries only `error` plus `artifact_identifier` alongside that known durable operation identifier; and `maintenance_result_transfer_interrupted` carries only `error`, explicit target digest, and `maintenance_result_identifier`. None carries operation state, semantic failure, recovery evidence, terminal disposition, certainty, destination path, or staging path.

The Rust enum uses fully spelled variant names corresponding one-to-one with these external tags. A receipt, nonterminal status, list page, maintenance result, or control report therefore never sits outside the advertised schema. Neither a failed state nor a presentation-layer error flag establishes authority. CLI JSON and Plan 0007 use the same branch selection and canonical bytes.

Every inline dynamic name, state, error member, command result, descriptor, digest, suggested file name, URI component, maintenance fact, and capacity fact has a named byte/count bound. `MAXIMUM_MACHINE_OUTCOME_ENVELOPE_BYTES` is strictly below the pinned FSM 4096-byte canonical structured acknowledgement cap; boundary tests serialize both maximum conditional recovery-evidence branches, every conditional terminal branch including result unavailable, the largest inline maintenance values, and the fixed `maintenance_result_access` reference below, at, and above the Slingshot maximum. No assertion requires a complete maximum maintenance manifest or receipt itself to fit below 4096 bytes. The daemon/local outcome contract returns a canonical operation `structured_result` artifact disposition or maintenance-result association whenever the corresponding logical value cannot fit inline; renderers validate and preserve that shared disposition rather than making an independent choice. Each operation-artifact access entry contains its `ArtifactDescriptor` plus the same target digest and a canonically percent-encoded access URI with no filesystem path. Maintenance access uses the exact closed entry and URI above, retains the selected target and canonical content digest needed to authenticate the metadata lookup, and has no operation identity or slot. The command-artifact projection is structural: for example, a load Artifact result retains its requested path and replaces only its descriptor leaf with that access entry. Progress remains standard error and never changes the final envelope. Broken standard output is a classified local-output failure rather than a remote retry.

The exit taxonomy is a public mapping backed by named constants: success `0`, invocation `2`, profile/configuration `3`, daemon bootstrap or local transport `4`, authentication or authorization `5`, authoritative nonexecution or agent rejection `6`, authoritative terminal remote failure `7`, and pending, result-unavailable, or fail-closed-indeterminate operation outcome `8`, internal invariant `9`, and interrupt `130`. The mapping switches on Plan 0005's exact terminal kind/disposition pair, never on a semantic failure-name prefix or lifecycle state: `AuthoritativeNonExecution` maps to `6`; `AuthoritativeRemoteFailure` maps to `7`; `FailClosedIndeterminate` maps to `8`; and the only legal terminal `AuthoritativeRemoteSuccess` pair, `ResultUnavailable`, maps to `8` while reporting that remote work succeeded and only its required result is unavailable. The full semantic failure object is retained independently of that exit choice, including outcome-unknown categories, so classification cannot erase or alias it. Every nonterminal `RecoveryRequired` branch also maps to `8`, including post-success result acquisition.

Interrupt rendering is phase-specific and linearized against durable-receipt validation, result publication, and the final renderer commit. Before a receipt is validated, the client makes no durable-admission claim: it preserves the exact generated or caller-supplied identifier as `retry_operation_identifier`, JSON emits exactly one `local_application_error/submission_interrupted_before_receipt` envelope with `admission: "unknown"`, human stdout is empty, and human stderr is exactly `interrupted before durable receipt; admission unknown; retry operation <retry_operation_identifier>`. After a receipt is validated while waiting for state or result, JSON emits exactly one `local_application_error/operation_observation_interrupted` envelope containing the known accepted/replayed admission and revision plus the durable operation identifier; human stdout is empty and stderr is exactly `interrupted; operation <operation_identifier> remains durable and observable`. Before local operation-artifact publication, JSON emits exactly one `local_application_error/artifact_transfer_interrupted` envelope containing the durable operation and artifact identifiers but no path or claim about staged bytes; human stdout is empty and stderr is exactly `interrupted artifact transfer <artifact_identifier> for operation <operation_identifier>; rerun to resume`. Before local maintenance-result publication, JSON emits exactly one `local_application_error/maintenance_result_transfer_interrupted` containing only the selected target digest and maintenance-result identifier; human stdout is empty and stderr is exactly `interrupted maintenance result transfer <maintenance_result_identifier> for target <author_target_identity_digest>; rerun to resume`.

Atomic artifact publication itself is a success commit, not an intermediate transfer phase. A handled signal that is first observed at or after that commit is deferred through the bounded final success-rendering critical section and cannot change exit `0` or the success bytes into an interrupt. If forced process/output loss prevents a complete rendering, the retained exact publication receipt makes the next identical invocation authenticate the already-published destination and re-render that same success without collision, transfer, or remote access. A completely committed non-artifact final success/failure rendering likewise wins over a later signal; otherwise exactly one applicable pre-publication interruption rendering wins. Every rendered interruption exits `130`, unregisters only the local waiter or downloader, sends no daemon/agent cancellation, and changes no durable operation state.

## 0028 — Process Contract Proof

`slingshot-test-support` supplies a product-independent process harness with isolated environment and filesystem roots, captured byte streams, signals, terminal/no-terminal modes, and bounded instance ownership. It consumes Plan 0001's platform capability contract and Plan 0004's retained-control contract rather than discovering descendants by process identifier. Every directly owned child retains its instance-bound child/native process handle or supervision channel continuously from creation through reap. Responsive daemon cleanup obtains the current live instance nonce and uses cooperative `daemon.stop`; unresponsive owned-child cleanup acts only through that retained handle/channel. Process identifiers are diagnostics only: the harness never enumerates descendants by process identifier and never checks a process identifier and later signals it. A stale nonce or retained handle for a reaped instance cannot stop a replacement, including after process-identifier reuse. The harness has no dependency on the command-line, daemon, configuration, or development crates; product suites provide the nonce-bound protocol adapter while the generic harness owns only the stable process primitive.

Command-line integration tests compose that generic harness with scripted local-protocol endpoints and compiled Slingshot processes. Golden sessions cover every command; authentication of the canonical-JSON artifact/manifest/annotation relationship; exact five-field catalog acceptance and independent canonical-contract/limits/argument-schema/result-schema drift refusal; raw-byte then Draft 2020-12 then typed conversion; canonical phrase/asset/token inputs; every revised closed semantic failure in both output modes; exact closed Plan 0002 configuration diagnostics without provenance leakage; configuration check without daemon or network access; explicit daemon lifecycle; target-revision mismatch; absent/reused/concurrent auto-start; detached and attached operation paths; post-admission lost-receipt replay from a new process; bounded list and maintenance metadata/read/preview/apply/result through replay/restart/ownership transfer/supersession/retirement; every exit category; operation-artifact and maintenance-result publication/render receipt recovery; broken output; early daemon exit/readiness failure; and the four interruption variants in terminal and redirected modes. Cleanup fixtures cover responsive current-nonce stop, unresponsive retained-handle termination, stale nonce, owner replacement, and process-identifier reuse without killing an unowned process.

Every fixture secret is unique and scanned across standard output, standard error, process arguments, structured envelopes, golden diffs, and tracing capture. The reference document is rendered from the same command metadata used by parsing and compared with a committed snapshot, so help, registry coverage, examples, exit values, and documentation cannot drift independently.
