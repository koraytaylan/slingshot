# Plan 0010 — Operational Command Surface — ✅ Complete

The roll-up row in [../STATUS.md](../STATUS.md) must stay in sync with this file. Task-level truth lives in [tasks/](tasks/) frontmatter; Makina's integration coordinator updates both layers.

- **Status:** ✅ Complete.
- **Goal:** publish sixty-four commands instead of twelve, so that page and component lifecycle, asset lifecycle, content and experience fragments, Open Service Gateway Initiative platform state, resource mapping and resolution, workflow management, Sling job management, authorizable administration, and replication queue control are each one bounded typed command rather than a browser tab.
- **Root cause:** twelve rows cover one console. Half of them are one side of a pair whose other side does not exist - a page can be created and never changed or removed, an asset can be searched and never written, a configuration can be read one identifier at a time and never listed, content can be offered to replication and the queue that accepted it can never be examined - and every operational question outside that console leaves the executable entirely.
- **Approach:** land the operational limits and the six validated vocabulary leaves first; then one independently tested command contract per operation, each with canonical fixtures, boundary proofs at and one step past every bound, exact no-effect failure documents, and language-neutral agent-conformance scenarios; then one sixty-four-row registry in ascending wire-name order under an access definition widened from repository content to any state the author retains, both role schemas with committed bytes and digests, the command-line builders and options that construct every new command, and the rendered reference and compatibility surfaces that are checked against the registry rather than written beside it.
- **Progress:** 60/60 tasks done; 0 blocked; 0 dropped.
- **Integration:** `complete`; run `develop`; base `main` @ `11c2e531d8a07a885321e7a09b1dccc623a733cf`; validation base `e1152a1b1cf8a78877b3a0f372e7635779bd85e4`; mode `sequential`; final integration `pending`.
- **Exceptions:**
  - **4001's recorded footprint named the manifest and its test and nothing that records the manifest's digest.** Three committed documents record that digest rather than compute it - the catalog fixture, the schema manifest, and the protocol compatibility snapshot - so extending the manifest leaves all three disagreeing with the build, and the gate refuses the tree until they are regenerated. They are the task's own consequence and belong in its footprint, so the footprint was corrected in its own change before the task landed.
  - **Every task that adds a command leaf also owns its row in the command module inventory and its own status stamp, and no task's footprint said so.** The family keeps one list of its leaves in `crates/slingshot-domain/tests/fixtures/command-module-inventory.txt`, and an assertion compares that list, the family root's declarations, and the files on disk in both directions, and refuses a leaf that holds code while its owning task still reads as planned. A leaf therefore cannot land without its inventory row and its status, so both were added to every leaf-adding task's footprint in one change before the first of them landed.
  - **4002 owns making the shared address shape reusable, which its footprint did not name.** Nine repository address values already share one macro-declared shape, and the four vocabulary leaves are the same shape again. The choice was to copy that shape into four more modules or to make the one that exists visible to the family; the second is the repository's own rule about a thing existing once, so `repository_path.rs` joined 4002's footprint and its own constructions were routed through the single constructor the shape now declares.

  - **The vocabulary leaves share three shapes, and each was about to be written four times.** A nonempty ascending requested-state set, the rule that an opaque identifier refuses a control and an edge space, and the validated-address wrapper are each one thing four leaves need. They were hoisted into the leaf that already owns their kind - the requested set into the listing leaf, the identifier body rule beside the address bound rule - and 4003 and 4004 gained those two files in their footprints and the listing leaf in their dependencies, before either landed.
  - **Five update commands carry the same pair of documents, so 4006 owns the pair.** The removal list, the refusal of a property named in both documents, and the refusal of a mutation that changes nothing are the shared mutation vocabulary rather than `update_page`'s, so they were added to 4006's steps instead of widening 4101's footprint to reach the same leaf.

  - **An instance's start time is a JCR instant, and that value had no wire form of its own.** `DateTimeString` was reachable only inside a property value, so a result carrying one directly could not be written or read. It gained the serialization its canonical spelling already implied - one string, validated on the way in - and `property_value.rs` joined 4703's footprint rather than the instant being restated as an unvalidated string beside it.

  - **The byte contract grew, so every schema digest moved - including the twelve that existed before.** Each new listing is ordered by a member the canonical-JSON contract had no comparator for, so the contract gained twelve comparators that name the member each orders by. Every role schema carries that contract's digest as an annotation by design, which is what binds the byte rules into a schema's identity, so extending the contract regenerated all one hundred and twenty-eight schemas and moved all one hundred and twenty-eight digests. The compatibility snapshot is the thing that notices, and it was refreshed under its own review variable rather than silenced. Nothing has consumed the old digests: no package is published and no release artifact exists. The alternative - bumping sixty-four semantic versions for sixty-four commands whose meaning did not change - would have recorded a change that did not happen.
  - **The catalog was being rebuilt on every question, and it had become expensive enough to break something.** `CommandCatalog::published()` writes one hundred and twenty-eight canonical schema documents and digests every one, and the command line asks for the catalog several times while parsing a single invocation. At twelve commands that was invisible; at sixty-four it delayed startup enough that a signal sent to an interrupted run arrived before the handler was installed, and the run died by signal instead of exiting one hundred and thirty. The catalog is now built once and handed out as a copy, which the interrupted-session assertion was the thing that caught.
  - **5103's footprint named a file the work did not need.** The plan expected the option table to outgrow `invocation.rs` and named `invocation_options.rs` for it. Thirty-eight new options left the file inside the size rule, so the split would have been a second file for no reason; the footprint was corrected instead, and the plan now says to split only if the limit is actually reached. The same task gained `commands/operational_values.rs`, which the plan had not named: ten families read the same handful of shapes off a command line, and ten copies of that reading would be ten chances to accept a spelling the domain refuses.
  - **Two limits this plan declared were a second name for a bound that already existed, and were removed.** `MAXIMUM_WORKFLOW_TITLE_BYTES` named the same thing `MAXIMUM_PAGE_TITLE_BYTES` names, because a workflow's title is the same bounded title value every other title in this registry is; and `MAXIMUM_OPERATIONAL_EXECUTION_DURATION_MILLISECONDS` named the same budget the discovery duration already bounds, since every windowed command in this plan allows the shared discovery failures. A limit that exists twice is a value that can drift from itself, which is the rule the manifest exists to keep, so both were taken out and the architecture's tables corrected. An assertion that every declared limit is read by Rust was written and then removed: many limits are normative for the separately built agent and are read by nothing here, so the assertion would have been a rule against being explicit with the agent.

  - **Two tasks in two plans shared an identity.** Plan 0003 already had a task called `command-schemas`, and the workspace module map refuses two tasks with one identity because a footprint would then belong to both. This plan's became `operational-command-schemas`.

- **Outcome:** Sixty-four commands where there were twelve, under one registry, one ascending order, and an access classification widened from repository content to any state the author retains. Page and component lifecycle, asset lifecycle, content and experience fragments, configuration search and change, bundle and component inventory and lifecycle, resource mapping and resolution in both directions, workflow models and instances and their control, Sling queues and jobs and their cancellation, authorizable creation, profile, disablement, removal and membership, and replication agents, queues, flushes and retries are each one bounded typed command with committed schemas, canonical fixtures, boundary proofs at and one step past every bound, exact no-effect failure documents, a command-line leaf, and a Model Context Protocol tool. No command transports a credential and none can: a created user has no password, a configuration update answers with a count, a job inspection reports keys and no values, a configuration listing reports no value at all, and a replication agent reports a transport kind and never a transport address. Every destructive content command states its reference policy, every guard - an expected kind, an expected queue length, a self-membership, a destination inside its own source - is an argument rather than a convention, and every deletion refuses an absent target rather than reporting success.
