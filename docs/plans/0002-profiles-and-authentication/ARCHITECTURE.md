## Exact configuration grammar

Profile, selection, and configuration-snapshot documents are TOML 1.0.0 UTF-8 without a byte-order mark or NUL. Every string-bearing field uses a one-line TOML basic string; literal and multiline strings are rejected. A profile root contains exactly `format_version`, `name`, and `environments`. `format_version` has exact source token `1`, `name` follows the manifest grammar, and `environments` is a nonempty table with at most `MAXIMUM_ENVIRONMENTS_PER_PROFILE` uniquely named members. Each environment contains exactly `deployment`, `author`, `publisher`, `authentication`, optional `additional_ca_certificate_file`, and optional `allow_insecure_author_transport`. `author` and `publisher` each contain only `base_address`. Basic authentication contains exactly `method`, `user_name`, and `password`; Cloud authentication contains exactly `method` and `credentials_file`. The optional insecure field has exact source token `true` only in the one valid non-loopback Adobe Experience Manager 6.5 Basic case; explicit `false` is rejected as meaningless. A selection root contains exactly `format_version = 1`, `profile`, and `environment`. The required configuration-snapshot root contains exactly `format_version = 1` and nonempty `sources`; `sources` is an array of one through `MAXIMUM_CONFIGURATION_SNAPSHOT_SOURCES` tables containing exactly `reference` and `sha256`, strictly ascending by canonical reference bytes with no duplicate. Each reference uses the portable root-relative grammar and each digest is 64 lowercase hexadecimal characters over the exact source bytes. The source set contains every profile document, optional `selection.toml`, and exactly every credential/certificate reference reachable from those profiles; it excludes `configuration-snapshot.toml` itself and admits no surplus source. Dotted-key aliases, duplicate keys/tables, arrays outside this exact snapshot inventory, and unknown members are invalid.

The `profiles` directory is nonrecursive. Before extension filtering, all entries count toward `MAXIMUM_PROFILE_DIRECTORY_ENTRIES`; every entry must be an ordinary file whose complete name fits `MAXIMUM_PROFILE_FILE_NAME_BYTES` and consists of a nonempty portable reference-component stem plus exact lowercase `.toml`. Unsupported entries are errors, not ignored. A root-contained credential or certificate reference uses `/` on every platform, consists of one through `MAXIMUM_CONFIGURATION_REFERENCE_COMPONENTS` manifest-grammar components, and fits both component and complete-reference byte bounds. Backslash, empty/dot/dot-dot component, leading slash, drive/prefix/Uniform Naming Convention form, trailing separator, alternate separator, or normalization-changing spelling is invalid.

Profile/environment names are ASCII and byte-counted. Basic usernames/passwords and Cloud nonsecret identifiers are counted as UTF-8 bytes before construction; usernames are nonempty, contain no colon, U+0000 through U+001F, or U+007F, and receive no Unicode normalization. The password may contain a colon but not NUL and is preserved as exact UTF-8 bytes in `SecretValue`. The service-credential `technicalAccount.clientId` is nonempty ASCII RFC 3986 unreserved bytes; a metascope is one through `MAXIMUM_METASCOPE_BYTES` lowercase ASCII letters, digits, or underscore, and the comma-separated input has no whitespace, empty member, or duplicate. Organization identifier, technical-account identifier from `integration.id`, and email values are nonempty UTF-8 with no C0/DEL control and receive no Unicode normalization.

A tier base address is measured before parse and again after canonical serialization. Its scheme is case-insensitive input rendered lowercase. A host is an ASCII Domain Name System name, canonical dotted-decimal IPv4, or bracketed IPv6; Unicode/Internationalized Domain Name input, zone identifiers, trailing root dot, empty label, and noncanonical IPv4 are rejected. Domain Name System labels are at most 63 bytes, use ASCII letters/digits/hyphen without edge hyphen, render lowercase, and the host fits the manifest limit. A base-ten port is 1 through 65,535 with no sign; explicit scheme-default 80/443 normalizes to omission. There is no user information, query, or fragment. Empty path and `/` normalize to root. A non-root prefix begins with one slash, has no trailing slash, and fits all manifest path bounds. Percent triplets accept either hexadecimal case and render uppercase; percent-encoded unreserved bytes decode to their literal spelling, literal non-ASCII is UTF-8-percent-encoded, and the decoded segment must be valid UTF-8. Empty/repeated segments, decoded dot/dot-dot, encoded slash/backslash, NUL/C0/DEL, or a second decode that changes a segment is invalid. No Unicode normalization occurs. IPv6 renders under RFC 5952. Endpoint append applies the same segment encoder and cannot replace the prefix.

## 0005 — Profile Documents

Endpoint construction appends individually encoded segments and never URL-joins away the prefix.

Cloud author and publisher addresses require TLS. Adobe Experience Manager 6.5 loopback author cleartext is allowed by default only for exact `localhost`, `127.0.0.1`, or `[::1]`. Non-loopback author cleartext requires `AllowInsecureAuthorTransport`, serialized as `allow_insecure_author_transport = true`; the opt-in is legal only with Basic Adobe Experience Manager 6.5 and only for that non-loopback cleartext case. An environment always contains author and publisher metadata. The selected connection target is exposed through an author-only method; no general tier-to-connection conversion exists. It yields normalized sources/names, typed environment, name-only namespace, and optional insecure-author warning only from one complete committed source generation. Complete identity is finalized after snapshot construction has resolved the authentication principal, canonical metascope set, immutable platform-only identity-management trust snapshot, and distinct immutable author trust snapshot. The pure identity builder consumes the exact closed preimages above and produces `AuthorTargetIdentity` plus `SelectedEnvironmentRevision`; it accepts no map iteration, TOML bytes, private source digest, timestamp, or filesystem metadata. The inventory inspector performs only per-document profile/selection syntax, shape, and semantics needed to derive roles. It preserves individually typed documents and the requested selection names but does not decide cross-document profile-name uniqueness, profile/environment existence, or default selection. After `VerifiedConfigurationGeneration` proves S2, the profile loader validates name uniqueness and task `validate-profile-selection` resolves the explicit/default pair against that unique collection, preserving the manifest failure precedence.

## 0006 — Credential File Boundary

The source-role inventory assigns each canonical reference exactly one of `profile`, `selection`, `service_credentials`, or `additional_certificate_authority`. Bounded directory discovery identifies every profile reference before source retention. A handle-relative no-follow optional-presence observation of exact `selection.toml` must agree with S1; agreement identifies the optional selection reference without a path reopen. The coordinator applies those two smaller class-specific limits before lending either document to the inspector. Other listed sources remain role-unknown under the generic source limit until the inspector derives their credential/certificate roles from bounded profile TOML, after which their class-specific limits apply. A canonical reference repeated within one role is deduplicated for inventory equality, but using one reference in two roles, using the fixed snapshot/selection/profile location as credential or certificate content, or classifying a discovered profile under another role is `configuration_snapshot_inconsistent`. Class-specific size checks and selected parser dispatch therefore have one unambiguous authority.

`ConfigurationRootResolver` gives the product spelling `~/.config/slingshot` one exact non-shell meaning and samples the account identity once for both root resolution and ownership checks. Linux and macOS query the operating-system account database for the effective user identifier; Windows queries `FOLDERID_Profile` for the current process-token user. The result must be one nonempty absolute Unicode native path. Missing, multiple/ambiguous, relative, empty, non-Unicode, wrong-user, or operating-system lookup failure returns a stable typed configuration-root error before any document open. `HOME`, `XDG_CONFIG_HOME`, `USERPROFILE`, `HOMEDRIVE`, `HOMEPATH`, working-directory state, and literal shell tilde expansion are ignored. The resolver appends exact `.config` and `slingshot` components and obtains the root by absolute directory-handle traversal with the same no-follow/reparse and identity rules as descendant access. Tests inject a typed fake account resolver and an explicit test root; no production process argument or environment variable can override the root.

Configuration references resolve from that canonical Slingshot configuration-root handle, never the process working directory or a profile's directory. Lexical validation rejects absolute paths, empty components, parent traversal, platform prefixes, and cross-platform separators. The filesystem authority opens every descendant without following links and accepts only a bounded ordinary final file owned by the sampled current-user identity with exactly one hard link; a second directory entry could otherwise mutate the same object outside the verified root and is rejected even when both entries have the same owner. `configuration-snapshot.toml`, every profile TOML, optional `selection.toml`, service-credential JSON, and additional certificate-authority file use this current-user boundary; privileged operating-system principals retain their ordinary ability to bypass or receive operating-system access, but no unprivileged principal receives file data or mutation rights. On Linux the authority requires the sampled effective user identifier as owner, binds device/inode/type/link evidence to the same descriptor, requires descriptor link count exactly one, and queries the POSIX access-control list from the descriptor rather than relying on mode bits alone. It expands named-user/named-group entries through the access-control-list mask: a file rejects every effective group/other or named non-owner read, write, or execute permission, while a directory rejects every effective non-owner write/create/delete permission; a directory default access-control list is evaluated under the same prospective rule. On macOS it applies the same descriptor-bound owner/mode/device/inode/type checks, requires descriptor link count exactly one for the final file, and queries extended access-control-list state from that same open descriptor; this semantic version requires no extended access-control-list entries, so a nontrivial allow or deny entry fails instead of being ignored. On Windows the authority uses the same sampled process-token user Security Identifier and defines exactly three trusted principals: that sampled identifier, LocalSystem `S-1-5-18`, and BUILTIN\Administrators `S-1-5-32-544`. Every root/descendant owner Security Identifier must equal the sampled user. The Slingshot root discretionary access-control list is protected from its external parent; every root/descendant list is canonical, and an unprotected descendant may contain inherited entries only when they are exactly traceable to its already verified Slingshot parent. The authority rejects every reparse-point component, requires final-file link count exactly one, and identifies an open object by volume serial number plus 128-bit file identifier. A null/absent list, noncanonical list, untraceable inherited entry, object/callback/conditional entry, unresolved generic mask, or other entry whose effective target rights cannot be computed is rejected. After expanding generic masks and inherited flags, any of the three trusted principals may hold data and control rights; every other Security Identifier may hold only `READ_CONTROL` and `SYNCHRONIZE`, with no file/directory data, execute, create, write, append, delete, permission-change, or ownership right. Deny entries are evaluated before allow entries and cannot be used to excuse a forbidden untrusted allow. The root and descendants are opened relative to verified directory handles; no validation-then-reopen path exists.

Each stable-read attempt uses one already verified final-file handle. It captures pre-read identity and mutation metadata, reads bounded byte sequence A from offset zero through the observed exact length and end of file, captures middle evidence, rewinds that same handle, reads independently bounded byte sequence B from offset zero through the newly observed exact length and end of file, and captures post-read evidence. Linux/macOS evidence is device, inode, ordinary-file type, link count, byte length, modification timestamp, and status-change timestamp from that descriptor; Windows evidence is volume serial number, 128-bit file identifier, ordinary-file type, link count, end-of-file length, last-write time, and change time from that handle. Acceptance requires pre/middle/post evidence byte-for-byte equal, A equal to B, both reads to reach end of file at the recorded length, and the ownership/access policy to remain valid on the same handle. Any short/growing read, evidence change, or byte mismatch closes the attempt and restarts the complete root-relative no-follow open/verification sequence once. A second unstable attempt fails as `configuration_file_changed_during_read` without returning bytes. Because an already-open handle truthfully continues to name its old object across an atomic directory-entry replacement, a per-file read promises complete old-or-new bytes, not replacement detection.

Cross-file atomicity comes from required `configuration-snapshot.toml` and generic `ConfigurationGenerationCoordinator`. On each attempt up to `MAXIMUM_CONFIGURATION_GENERATION_ATTEMPTS`, startup stable-reads snapshot bytes S1, parses its closed sorted source/digest inventory, and boundedly enumerates the profile directory. It stable-reads every listed source through the same authority under `MAXIMUM_CONFIGURATION_SOURCE_DOCUMENT_BYTES`, privately verifies its exact SHA-256 digest, applies already known profile/selection limits, and checked-adds its stable recorded byte length before retaining it; a source whose length would make the sum exceed `MAXIMUM_CONFIGURATION_GENERATION_SOURCE_BYTES` is rejected before its bytes are retained. The coordinator invokes an injected bounded `ConfigurationSourceInventoryInspector` over the preclassified profile/selection documents and generic-bounded remaining collection. The inspector parses only profile and optional selection TOML and returns typed inspection output plus the exact transitive role inventory. The coordinator requires that inventory to equal the sorted manifest inventory, applies credential/certificate class-specific document bounds, stable-reads snapshot bytes S2, and requires S2 equal S1 before returning `VerifiedConfigurationGeneration<Inspection>` with role-tagged opaque source documents. It has no profile-parser, credential-domain, JSON, PEM, trust, or key dependency; deterministic coordinator tests use a fake inspector. Only after this S1/source/S2 proof does selection consume the chosen service-credential document in the task-0701 JSON parser and the chosen additional-certificate-authority document in the task-0604 PEM parser. Unselected opaque credential/certificate documents are discarded without semantic parsing. The first successful attempt returns immediately; exhausting the two whole-generation attempts on missing, mixed, changed, unlisted, surplus, aggregate-over-limit, or digest-mismatched state yields only `configuration_snapshot_inconsistent` without exposing either digest or source content. A writer creates and synchronizes every safe temporary source, atomically replaces and synchronizes those entries, and atomically publishes the new snapshot file last with its directory synchronized. Startup therefore accepts one complete committed generation or none; an already constructed snapshot never reloads. The private source digests are secret-adjacent comparison values and never enter identity, diagnostics, logs, or wire. This protocol detects ordinary concurrent edits but explicitly does not claim isolation from an actively malicious process running as the same account that can rewrite the sources and commit manifest and manipulate metadata. Such a writer is inside the operating-system-account trust boundary. The deterministic policy fake exercises every supported platform row, every per-file pre/read/middle/read/post race, old-handle rename behavior, exact aggregate boundary, mixed-generation boundary, and before/after snapshot publication. A native invocation may report only the one exact Plan 0001 row matching its current environment and is explicitly untrusted implementation evidence; Plan 0009 alone maps providers and authenticates aggregate evidence for all supported rows.

All configuration-source bytes are sensitive regardless of source role. `SensitiveConfigurationDocument` is their bounded temporary owned representation during stable reading, private digest verification, inventory inspection, and selected-source parsing. Its `Debug` and `Display` are the exact ASCII `[REDACTED]`, it has no serialization, equality, ordering, hashing, cloning, or general byte-returning interface, its narrowly named digest/inspection/parse operations lend bytes only for the call, and its mutable owned buffer is zeroized on drop. A parser may create immutable dependency-owned buffers transiently inside that call; no zeroization claim covers those buffers, operating-system copies, allocator internals, or bytes outside Slingshot ownership, and the parser must not retain them. `SecretValue` is the only long-lived typed representation of an extracted password, private key, client secret, signed assertion, or access token after extraction. It has the same redacted formatting and lack of serialization/equality/hash/order, exposes bytes only through a narrowly named closure, and zeroizes its owned mutable buffer on drop and replacement. Parsers move extracted secrets promptly into `SecretValue`; snapshot construction disposes all source and parser buffers after retaining only typed values. Error types hold only manifest failure codes and manifest-vocabulary structural locations within `MAXIMUM_DIAGNOSTIC_STRUCTURAL_LOCATION_BYTES`, never a source reference/value or a digest/comparison value derived from secret bytes. The tracing filter applies the same classification to request metadata and exchange failures.

At startup the supported-platform trust adapter takes one bounded snapshot of platform server-authentication roots. For every provider record it resolves the effective trust purpose before retaining DER: the record must be an X.509 certificate authority unconditionally permitted for Transport Layer Security server authentication, with no provider distrust/deny, application/policy/name restriction outside the certificate bytes, or unevaluable trust setting; an Extended Key Usage extension, when present on the anchor, must include server authentication. The adapter rejects unavailable, partial, purpose-ineligible, externally constrained, unevaluable, over-count, over-entry, over-canonical-byte, or non-CA input as `platform_trust_snapshot_invalid`; repeated DER is accepted once only when every provider record yields the same unconditional server-authentication decision, and a conflicting duplicate rejects the snapshot. Consequently DER fully represents every accepted platform anchor's effective server-authentication policy and rebuilding an immutable verifier cannot broaden provider trust. The unique sorted platform DER set is encoded under `slingshot.verified-identity-management-trust-policy/1`, hashed as `VerifiedIdentityManagementTrustPolicyIdentity`, and is the complete and only root input accepted by the identity-management client builder.

An optional additional certificate-authority source from the verified generation is an author-only trust extension and must fit `MAXIMUM_ADDITIONAL_CERTIFICATE_AUTHORITY_DOCUMENT_BYTES`. It contains one through `MAXIMUM_ADDITIONAL_CERTIFICATE_AUTHORITIES` exact `CERTIFICATE` PEM blocks with only ASCII space, horizontal tab, carriage return, or line feed between blocks. Each strict RFC 7468 standard-Base64 block decodes to one nonduplicate X.509 DER certificate within `MAXIMUM_ADDITIONAL_CERTIFICATE_AUTHORITY_DER_BYTES`; it must have Basic Constraints `CA = true`, Key Usage `keyCertSign` when Key Usage exists, and server authentication when Extended Key Usage exists. Every other PEM label, encrypted/private-key block, surplus text, duplicate DER certificate, end-entity certificate, malformed certificate, or excess fails before client construction. The unique sorted union of platform roots and selected additional author roots is encoded under `slingshot.verified-author-trust-policy/1` and hashed as `VerifiedAuthorTrustPolicyIdentity`. The author client builder accepts only that union; the identity-management builder's input type accepts only the platform snapshot and cannot accept an additional-certificate document, additional DER, the author union, or its identity. Both route-specific immutable root stores originate from the same completed selected startup snapshot, use TLS 1.2 or 1.3 with ordinary hostname and certificate-constraint validation, install no redirect policy, proxy connector, or automatic decompression, and ignore system proxy discovery plus exact case variants `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`, `http_proxy`, `https_proxy`, `all_proxy`, and `no_proxy`. A later operating-system root-store or source edit cannot affect either live client; an explicit daemon restart snapshots both again and a change in either route's effective set changes the revision before recovery. Additional roots never replace platform roots, enter identity-management trust, or create client authentication. Publisher remains metadata and is never passed to either client builder.

## 0007 — Cloud Token Exchange

The service-credential parser consumes only the selected role-tagged `SensitiveConfigurationDocument` from a completed `VerifiedConfigurationGeneration`. It accepts a UTF-8, no-byte-order-mark, duplicate-aware JSON document within `MAXIMUM_SERVICE_CREDENTIAL_DOCUMENT_BYTES` and `MAXIMUM_SERVICE_CREDENTIAL_JSON_DEPTH`, with exact top-level `ok: true`, `statusCode: 200`, and `integration` fields. Its closed `integration` object contains, in manifest validation order, `imsEndpoint`, `metascopes`, `technicalAccount`, `email`, `id`, `org`, `privateKey`, and `publicKey`; `technicalAccount` contains only `clientId` and `clientSecret`. Every string uses its independent manifest byte limit. The private key is one unencrypted PKCS #1 or PKCS #8 RSA PEM key whose modulus is within the manifest bit interval and exponent is exactly 65,537; `publicKey` is one X.509 `CERTIFICATE` PEM block whose RSA key matches it. Thus the parser recognizes the wrapper status, technical-account email, and public certificate that genuine downloaded files contain even though token exchange does not transmit them. The Adobe `integration.id` value is the one `TechnicalAccountIdentifier`: it alone uses `MAXIMUM_TECHNICAL_ACCOUNT_IDENTIFIER_BYTES`, becomes the principal field `technical_account_identifier`, and supplies JSON Web Token `sub`. The distinct `technicalAccount.clientId` remains `TechnicalAccountClientIdentifier` and supplies form `client_id` plus the audience path. The parser promptly moves the private key and client secret into `SecretValue`, disposes its source/parser buffers when typed construction completes, passes exact decoded organization, client, and technical-account identifier UTF-8 values directly to the domain principal-identity constructor, and exposes only that opaque identity outside authentication construction. Same-tuple secret/key/certificate rotation therefore preserves identity, while changing any tuple member changes identity. `imsEndpoint` must equal the manifest's sole ASCII authority `ims-na1.adobelogin.com` byte for byte; uppercase, port, trailing dot, scheme, path, user information, query, fragment, non-ASCII, or another host is `identity_management_authority_not_allowed`. The client internally constructs only `https://ims-na1.adobelogin.com/ims/exchange/jwt`, with no credential-controlled URL component. Authority rejection precedes assertion/client-secret access. Other missing, duplicate, wrongly typed, empty, oversized, unknown, non-success-wrapper, malformed certificate, or nonmatching-key failures use the manifest registry and structural location only. Unknown key bytes, scalar excerpts, parser-library source snippets, and expected/actual values are never retained or rendered because any can contain a credential sentinel. A document shaped like deprecated Adobe Developer Console Service Account credentials fails as `service_credentials_deprecated_product` and the human diagnostic names the product distinction and links to both Adobe sources in `SCOPE.md`.

`ServiceCredentialAssertionBuilder` is pure. It receives the already key-pair-validated credential fields and samples an injected UTC wall clock exactly once. The observation must be available, nonnegative, and at most `MAXIMUM_SERVICE_CREDENTIAL_UTC_UNIX_SECONDS = 253,402,300,799`; it is floored to a whole Unix second only after that range check. The sampled second must then lie inside the public certificate's inclusive validity interval. Checked addition of `SERVICE_CREDENTIAL_ASSERTION_LIFETIME_SECONDS = 28_800` produces an `exp` no greater than 253,402,329,599, and the completed assertion must fit `MAXIMUM_SERVICE_CREDENTIAL_ASSERTION_BYTES`. The closed `RS256` protected header bytes are exactly `{"alg":"RS256","typ":"JWT"}`. The payload contains only: `iss` as organization identifier; `sub` as the `TechnicalAccountIdentifier` from `integration.id`; `exp` as that exact sum; `aud` as `https://ims-na1.adobelogin.com/c/{validated client identifier}`; and one `https://ims-na1.adobelogin.com/s/{metascope}: true` claim per unique validated metascope. Object members are ordered by ascending UTF-8 key bytes with no insignificant whitespace; integers use minimal unsigned decimal. A JSON string starts and ends with quote, emits quote as `\"` and reverse solidus as `\\`, emits every other accepted noncontrol Unicode scalar directly as its shortest UTF-8 bytes, never escapes solidus, and never emits `\u` or a surrogate spelling. Accepted claim strings already reject controls. No other header parameter or claim is emitted.

Compact JSON Web Signature serialization is exact RFC 7515 framing: unpadded RFC 4648 base64url of the protected-header UTF-8 bytes, one ASCII period, unpadded base64url of payload UTF-8 bytes, one ASCII period, and unpadded base64url of the signature. The signing input is exactly the first two encoded segments plus their intervening period. `RS256` is RSASSA-PKCS1-v1_5 over SHA-256 of that ASCII signing input; the signature is the modulus-width big-endian octet string before base64url encoding. Padding, whitespace, another alphabet, alternate JSON escape, leading-zero integer, or surplus segment fails the independent vectors. The one sampled wall-clock observation must lie inside the public certificate's inclusive not-before/not-after interval before signing; equality at either boundary is accepted. The fixed eight-hour `exp` may extend beyond certificate not-after because Adobe Identity Management Services evaluates the signed assertion at exchange, and no task silently caps it. Language-neutral fixtures pin exact header/payload/signing-input/compact bytes, signatures, lifetime and certificate boundaries, unavailable/out-of-range clocks, malformed keys, maximum assertion size, and error redaction. This wall clock is not used for access-token freshness.

`AdobeIdentityManagementExchange` is the only identity-management network client in this plan. After applying the manifest endpoint, immutable platform-only identity-management trust policy, and direct policy, it sends exactly one HTTP `POST` whose body contains ordered `client_id`, `client_secret`, and `jwt_token` fields to the accepted TLS endpoint. No other HTTP method is constructible, and the request never contains `Expect`, an upgrade request, or a credential-controlled header. Encoding is the WHATWG UTF-8 `application/x-www-form-urlencoded` algorithm: space is `+`, ASCII alphanumeric plus `*`, `-`, `.`, and `_` remain literal, every other byte is uppercase `%HH`; the three fixed field-name/equality/separator portions occupy 36 bytes and the exact reachable maximum is `36 + 768 + 12,288 + 12,776 = MAXIMUM_IDENTITY_MANAGEMENT_REQUEST_BODY_BYTES = 25,868`. Checked construction rejects the next byte before a network request starts. Redirects, proxies, and automatic decompression are disabled and duplicate/extra form fields are impossible. An actual three-hundred response is knowable only after one secret-bearing request reaches the original endpoint: it is never followed, its `Location` is never parsed or contacted, and it yields no token.

The seven manifest timeout values use one injected monotonic clock. Name resolution plus transport connection, TLS handshake, complete form write, response heads, complete response stream, consecutive body-byte idle, and the whole exchange respectively cannot occupy a task beyond their exact bound. The asynchronous client races each pending phase against cancellation and its applicable deadlines. Its adapter surfaces every decoded informational head, the final head, and the presence and fields of any trailer section instead of library-filtering them. Head accounting uses one protocol-independent canonical decoded representation after HTTP/1 or HTTP/2 syntax decoding: the three ASCII status-code digits plus line feed; then each field in received order as its lowercase ASCII name, colon, one space, exact decoded value bytes, and line feed; then one final line feed. The aggregate checked charge is therefore exactly `5 + sum(name_bytes + value_bytes + 3)`; the single-field charge is exactly `name_bytes + value_bytes`; duplicates each consume one field/count/charge; pseudo-header and wire compression bytes never participate. A trailer section has no status line and is charged as exactly `1 + sum(name_bytes + value_bytes + 3)` under the same single-field, count, and aggregate-section limits. A control-bearing/invalid name or value fails transport decoding before this representation. The decoder rejects before admitting the field that would exceed `MAXIMUM_IDENTITY_MANAGEMENT_RESPONSE_HEADER_BYTES`, `MAXIMUM_IDENTITY_MANAGEMENT_RESPONSE_HEADER_COUNT`, or `MAXIMUM_IDENTITY_MANAGEMENT_RESPONSE_HEAD_BYTES`; fixed status and terminal line feeds are charged even with zero fields. After those charges, the first informational head—including 100, 101, or 103—is rejected as `identity_management_response_status_rejected`, the exchange is closed, and no later head/body/token is observed. A successful exchange has exactly one final status head. A final `Trailer` declaration is rejected as `identity_management_response_trailer_rejected` after final-status handling and before coding/media handling. After the body, the presence of any actual trailer section, including an explicitly empty section, is charged incrementally then rejected with the same code; no trailer collection is built without bounds. The decoder similarly rejects the next body byte beyond `MAXIMUM_IDENTITY_MANAGEMENT_RESPONSE_BODY_BYTES`. The manifest precedence applies at every checkpoint, equality expires, and arithmetic never wraps. Immediately before the first request byte can be written, the exchange records one injected monotonic lifetime anchor.

The client negotiates only HTTP/1.1 or HTTP/2 and never follows `Alt-Svc`, upgrades, or another protocol-migration signal. Before network use, its HTTP/1 field-line/parser bounds and HTTP/2 decoded-header-list plus compression-table bounds are configured from `MAXIMUM_IDENTITY_MANAGEMENT_RESPONSE_HEADER_BYTES`, `MAXIMUM_IDENTITY_MANAGEMENT_RESPONSE_HEADER_COUNT`, and `MAXIMUM_IDENTITY_MANAGEMENT_RESPONSE_HEAD_BYTES`; the adapter must reject incrementally before a dependency exposes an over-bound collection. The transport decoder admits only unambiguous protocol framing before exposing a decoded section: conflicting or invalid repeated Content-Length, simultaneous Transfer-Encoding and Content-Length, an invalid transfer-coding chain, HTTP/2 connection-specific fields, a pseudo-header ordering/duplication error, an over-bound compressed/decompressed header block, or bytes after the declared message boundary becomes `identity_management_transport_failed` or the earlier exact head-limit code under the manifest precedence. These errors never produce a partial status/body/token view.

Only final status 200 continues. It requires exactly one `Content-Type` whose media type is case-insensitive `application/json` with no parameter or exactly one case-insensitive `charset=utf-8`, zero or one `Content-Encoding` whose value is case-insensitive `identity`, no `Trailer` declaration, and an eventual stream end with no trailer section; duplicates, another parameter/charset/coding, decompression, or trailers fail. The duplicate-aware closed JSON object contains exactly nonempty RFC 9110 `token68` `access_token` within `MAXIMUM_ACCESS_TOKEN_BYTES`, exact lowercase `token_type = "bearer"`, and `expires_in` as a minimal unsigned JSON integer from 1 through `MAXIMUM_ACCESS_TOKEN_LIFETIME_MILLISECONDS`, measured in relative milliseconds. Only after complete stream end proves trailer absence and all deadline/byte checks pass does one body-receipt monotonic sample compute deadline as checked `anchor + expires_in`, never `receipt + expires_in`; head/body/trailer-end transfer time only consumes the advertised lease. Remaining duration must be strictly greater than checked `ACCESS_TOKEN_REFRESH_SKEW_MILLISECONDS + MINIMUM_ACCESS_TOKEN_USABLE_LEASE_MILLISECONDS`, exactly 360,000 ms. Elapsed/underflowed, equal, or shorter remainder is typed `AccessTokenLifetimeTooShort` with code `access_token_lifetime_too_short`; one millisecond above is accepted. A zero, negative, fractional, nonminimal, overflowing, absent, over-policy, malformed, wrong-token-type, or too-short response fails under the exact registry. A too-short response completes that one exchange flight, is never installed, and is not immediately exchanged again. Subsequent UTC wall-clock changes cannot alter the deadline. Identity-management exchange is authentication infrastructure; all Adobe Experience Manager traffic uses the selected author base address only.

## 0008 — Authentication Provider

`SelectedEnvironmentSnapshot` is assembled once during daemon startup only after the complete source generation passes its before/after commit-manifest proof. Basic construction derives `AuthenticationPrincipalIdentity` from the exact validated username and supplies the empty metascope set; Cloud construction takes the opaque identity and canonical metascope set produced from the parsed credential. The trust adapter supplies one immutable provider-policy-verified platform root snapshot and `VerifiedIdentityManagementTrustPolicyIdentity`, then derives the distinct immutable author platform-plus-selected-additional root snapshot and `VerifiedAuthorTrustPolicyIdentity`. The identity-management client can receive only the former and the author client can receive only the latter. Only then does the snapshot builder finalize immutable target identity/revision plus owned authentication and route-typed trust material and dispose every sensitive source/parser buffer. No provider method reloads a source or platform store. Editing or rotating sources affects only explicit stop/start. Same-principal password/private-key/client-secret/public-certificate/access-token rotation at the same normalized sources leaves `AuthorTargetIdentity` and `SelectedEnvironmentRevision` unchanged; a metascope or either route's effective trust change preserves `AuthorTargetIdentity` but changes the revision, and a username or Cloud principal-tuple change changes both.

`EnvironmentAuthenticationProvider` accepts a `SelectedEnvironmentSnapshot` and returns author-request authentication material. For Adobe Experience Manager 6.5 it creates byte-exact Basic authorization from validated username/password. For Cloud it obtains bearer token. It has no publisher method and refuses targets outside the complete author base. Non-loopback cleartext construction requires snapshot opt-in and warning status and emits that status to diagnostics without secrets; TLS and loopback cases carry no insecure warning. The identity-management path uses only the snapshot's platform-only route-typed roots, the author path uses only its platform-plus-selected-additional route-typed roots, and both bypass ambient proxies.

`CloudAccessTokenCache` lives behind the provider and only in daemon memory. Each immutable provider snapshot receives a process-random opaque `AccessTokenCacheIdentity`; it is unrelated to credential bytes, nonserializable, non-displayable, nonpersistent, and shared only by callers of that snapshot. An injected identity factory makes concurrency tests deterministic without creating a secret comparison oracle. A per-identity single-flight cell lets one caller refresh while concurrent callers await. The exchange and cache consume the same manifest `ACCESS_TOKEN_REFRESH_SKEW_MILLISECONDS` and `MINIMUM_ACCESS_TOKEN_USABLE_LEASE_MILLISECONDS` values. An exchange result is installable only after its receipt-time remaining lifetime strictly exceeds their checked sum; a typed too-short failure is delivered to every waiter, releases the flight, installs no token, and does not recursively start another flight. For an installed token, refresh skew compares an injected monotonic current value with the exchange's monotonic deadline; equality is refresh-required. Wall-clock movement has no effect after receipt.

Every installed Cloud token is applied through an opaque, nonserializable, non-displayable `AccessTokenLease` that carries a cache-internal checked installation generation unrelated to token bytes; generation exhaustion fails closed and never wraps. The provider exposes `refresh_after_unauthorized` only with that lease. Under the same cache-cell synchronization used for every refresh, the operation has four exact branches: a lease naming the usable current generation marks it unusable and zeroizes the cache-owned token buffer before starting or joining the cell's one refresh flight; a stale lease with a newer usable generation returns that generation without eviction or exchange; any lease presented while the current generation is unusable and a flight exists joins it; and an unusable generation left without a flight after failure/cancellation starts one retry. A scheduled refresh already in flight is that same flight, so an unauthorized response never creates a competing exchange. Concurrent unauthorized responses for one generation therefore converge on one replacement; failure or cancellation wakes every waiter, leaves the rejected generation unusable, releases the flight, and prevents fallback to it. Successful scheduled or forced refresh replaces atomically, and eviction zeroizes the access-token buffer owned by `SecretValue`. Assertions/private keys are never cached and access tokens, cache identities, leases, and installation generations are never persisted.

The two inward product crates retain focused boundary tests, while the outermost development crate owns and executes the composed transcript without reversing a product dependency. Plan 0009 owns authenticated all-row native evidence. All Adobe Experience Manager requests arrive only at author.
