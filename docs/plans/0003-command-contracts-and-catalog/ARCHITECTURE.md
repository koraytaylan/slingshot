# Plan 0003 — Command Contracts and Catalog

## Architectural boundary

slingshot-domain owns command meaning and performs no filesystem or network input and output. Its public command values are valid by construction: public constructors validate raw input, fields remain private where an invalid combination can otherwise be assembled, and serialization occurs only after validation. A command-specific result is structurally valid on its own but is not trusted as the result of an operation until the domain request-context validator compares its variant and every checkable echoed or command-derived invariant with the exact validated Command instance; adapters must perform that comparison before persistence, artifact acceptance, or forwarding. This pure validator does not claim provenance when two same-variant requests have no result field that distinguishes them. Plan 0005 completes exact request binding with the canonical submitted-command digest carried in the authenticated remote envelopes.

The crate exposes a Command enum at the end of this plan. Each variant wraps one command-specific argument type. Results remain command-specific rather than collapsing into an untyped JSON value. The author-agent protocol in Plan 0005 wraps these values without redefining them.

Canonical fixtures use the serialized wire field names. Rust identifiers use full words such as identifier, request, response, configuration, environment, authentication, hypertext_transfer_protocol, server_sent_event, model_context_protocol, adobe_experience_manager, and open_service_gateway_initiative. External product and protocol spellings remain intact in human documentation and wire media types.

## Shared rules

- Every list that must be non-empty has a validated wrapper.
- Every user-controlled string has a named byte limit.
- Every collection has a named item limit.
- Repository paths use the closed repository-name/path grammar below; they are absolute, start with one slash, contain no empty interior segment or traversal form, and have no trailing slash except for the root path.
- ResultWindow is a closed Initial or Continuation request. Initial contains offset and limit; Continuation contains only opaque ContinuationToken and cannot carry caller offset or limit. DEFAULT_RESULT_LIMIT and MAXIMUM_RESULT_LIMIT name Initial defaults/bounds.
- Serialized objects reject unknown fields.
- Optional fields are omitted rather than serialized as null; null is invalid in every command and command-result document.
- Command and result fixtures are canonical JSON and contain no credentials, endpoint addresses, runtime-generated timestamps, random values, or host paths. Fixed JCR Date values remain valid semantic fixtures.
- Error variants state the invalid field and the violated bound without echoing an entire potentially sensitive value.
- CommandSemanticContractVersion uses this exact bounded Semantic Versioning 2.0.0 ABNF, where `DIGIT = %x30-39`, `NONZERO = %x31-39`, `ALPHA = %x41-5A / %x61-7A`, and `HYPHEN = %x2D`: `numeric = "0" / (NONZERO *DIGIT)`; `core = numeric "." numeric "." numeric`; `prerelease-nonnumeric = 1*(DIGIT / ALPHA / HYPHEN)` with the additional requirement that at least one byte is `ALPHA` or `HYPHEN`; `prerelease-identifier = numeric / prerelease-nonnumeric`; `prerelease = prerelease-identifier *("." prerelease-identifier)`; `build-identifier = 1*(DIGIT / ALPHA / HYPHEN)`; `build = build-identifier *("." build-identifier)`; and `version = core ["-" prerelease] ["+" build]`. The complete ASCII version is at most 64 bytes. The identifier-count charge is exactly three core numeric identifiers plus every dot-separated prerelease identifier plus every dot-separated build identifier and must be at most 16. The ten-digit limit applies independently to each core numeric identifier and each all-digit prerelease identifier; it does not apply to build identifiers. Core and numeric prerelease identifiers use minimal spelling and reject a leading zero, while build metadata preserves its exact spelling and therefore `1.0.0+01` is legal. Empty identifiers, controls, Unicode, whitespace, slash, colon, question mark, number sign, and over-bound forms are invalid. Its accepted ASCII alphabet is emitted literally as one safe schema-URN segment. Every command introduced by this plan has exact initial semantic version `1.0.0`; no task chooses a different initial value.

## 0009 — Command Foundations

Plan 0001 creates and exports the empty `slingshot-domain::command` structural root only. Task 0901 adopts that root, solely owns the exact command leaf inventory, adds each empty compiling command leaf file/declaration named in this architecture, implements the shared bounded CommandSemanticContractVersion value in the foundation `command_identity` leaf, and commits the exact versioned command-limits manifest before command modules need either contract. It verifies the module and limits inventories so later command tasks mutate disjoint leaf files and consume rather than redeclare public constants. Plan 0001 carries no competing command-leaf or command-limit list.

repository_path.rs defines distinct RepositoryName, RepositoryPathSegment, RepositoryPath, RepositoryRelativePath, RepositoryPropertyPath, and errors. RepositoryName requires Unicode 15.1 NFC input and is either an unqualified local part or exactly one namespace prefix plus colon plus local part. A prefix is ASCII letter/underscore followed by ASCII letters/digits/underscore/hyphen/dot. A nonempty local part accepts Unicode scalar values except slash, colon, square brackets, asterisk, vertical bar, U+0000 through U+001F, and U+007F; it is not `.` or `..` and has no leading/trailing ASCII space. RepositoryPathSegment is one RepositoryName with an optional same-name-sibling suffix `[index]`. The first sibling omits a suffix; a suffix is valid only for a canonical base-ten index from two through MAXIMUM_SAME_NAME_SIBLING_INDEX, without plus or leading zero. `[1]`, zero, negative, and otherwise bracketed spellings are invalid, so one repository address has one canonical spelling.

RepositoryPath is root or slash-separated RepositoryPathSegment values with a leading slash. RepositoryRelativePath is one or more such segments without a leading slash. RepositoryPropertyPath is a closed Absolute(RepositoryPath) or Relative(RepositoryRelativePath) JCR Path property value and serializes as its exact canonical string. Read/load/query addresses permit same-name-sibling suffixes. PropertyName is one RepositoryName without such a suffix. PageName and ComponentName are separate creatable-child wrappers over an unqualified RepositoryName without a suffix; they are not interchangeable with path segments or property names. PrimaryNodeTypeName requires one qualified RepositoryName. Every wrapper has its own named byte/segment bound, requires already-normalized input rather than silently rewriting it, and preserves accepted spelling. Parent/address-child/creatable-child operations remain distinct and never concatenate unchecked text. Transport code alone percent-encodes Uniform Resource Locators.

RelativePropertyPath is a separate query role: zero or more RepositoryPathSegment child-resource addresses followed by exactly one PropertyName, with no leading slash. component_resource_type.rs defines ComponentResourceType because it is not a JCR name: it is a separately bounded absolute-or-relative slash-separated Sling resource-type spelling whose nonempty NFC segments reject colon, brackets, asterisk, vertical bar, controls, dot, dot-dot, and leading/trailing ASCII space; it has no same-name-sibling syntax. Canonical vectors cover Unicode normalization, malformed/multiple namespace colons, reserved punctuation, wildcard/pipe forms, same-name siblings, and cross-role rejection in Rust and external-agent fixtures.

result_window.rs defines ResultWindow::Initial { offset, limit } and ResultWindow::Continuation { continuation_token }, plus ResultOffset, ResultLimit, and ContinuationToken. Canonical JSON is exactly `{"mode":"initial","offset":...,"limit":...}` or `{"mode":"continuation","continuation_token":"..."}`; every object is closed. The named constants DEFAULT_RESULT_LIMIT, MAXIMUM_RESULT_LIMIT, MAXIMUM_RESULT_OFFSET, and MAXIMUM_CONTINUATION_TOKEN_BYTES are the sole source for defaults/bounds. A zero Initial limit or offset above its inclusive maximum is invalid, and Continuation rejects any offset or limit field even when offset is zero or limit equals the default. Initial offset counts fully evaluated matches, not raw repository candidates. Every candidate and property/criterion needed to decide a skipped match receives the ordinary checked discovery charges; a skipped match decrements the remaining offset after its match decision and receives no canonical-result byte charge. After the remaining offset reaches zero, emitted matches count toward ResultLimit and result bytes. Repository exhaustion after only skipped matches yields an empty terminal page. Computation exhaustion while skipping remains the ordinary no-partial discovery failure.

`slingshot.continuation-token/1` is the exact agent-owned protection contract. Its bounded canonical payload is one closed object with these exact members (shown in canonical UTF-8 key order): `arguments_digest`, `author_target_identity_digest`, `command_semantic_contract_version`, `command_wire_name`, `expires_at_unix_milliseconds`, `format`, `initial_result_limit`, `issued_at_unix_milliseconds`, `key_identifier`, and `resume_sort_key`. `format` is `slingshot.continuation-token/1`; the version is exact `1.0.0`; times are whole UTC Unix milliseconds; both digests are 64 lowercase SHA-256 hexadecimal characters; the key identifier equals the protected-header value; the limit is the originating Initial ResultLimit; and `resume_sort_key` is exactly the closed object `{"repository_path":"<last-emitted canonical RepositoryPath>"}` for every Plan 0003 discovery command. `slingshot.command-arguments-canonical/1` defines `arguments_digest` input as the validated command argument object with its exact `result_window` member omitted under the raw-byte, key/string/Boolean/integer/array/UTF-8, and typed ordered-collection rules of `slingshot.command-canonical-json/1`; no default, alias, presentation spelling, endpoint, credential, or token bytes participate. The AuthorTargetIdentity digest input is Plan 0005's canonical authenticated identity bytes. Issuance samples injected UTC once, uses checked addition of CONTINUATION_TOKEN_LIFETIME_MILLISECONDS, and refuses a value outside the representable range. Validation samples injected UTC once; equality with expires-at is expired, expires-at must equal issued-at plus the exact lifetime, and issued-at may be ahead of validation time by no more than MAXIMUM_CONTINUATION_TOKEN_CLOCK_SKEW_MILLISECONDS.

Plan 0005 owns the agent implementation, not the Plan 0003 Rust domain: the deployment must provide one durable continuation-key authority holding a persisted 256-bit operating-system-CSPRNG HMAC-SHA-256 key, a nonsecret bounded key identifier, and current-plus-previous-key rotation. That authority must enforce least-authority read/initialize/rotate access for the agent identity, secret-at-rest protection appropriate to the deployment, synchronized crash-safe atomic replacement, and restart-stable validation. Plan 0003 is provider-, topology-, storage-, and profile-neutral: it neither selects nor blesses a file, database, content property, environment variable, node-local cache, or another physical authority. Plan 0005 must refine this boundary with one deployment-compatible authority and fail closed when its durability, authorization, or continuity contract is unavailable. The command-specific canonical resume sort key fits MAXIMUM_CONTINUATION_RESUME_KEY_CANONICAL_BYTES before token construction. The compact token is exact unpadded base64url of canonical protected header, a period, unpadded base64url of the canonical payload, a period, and unpadded base64url of the 32-byte HMAC tag over ASCII role tag `slingshot.continuation-token/1`, one zero byte, protected-header bytes, one zero byte, and payload bytes. The protected header is exactly `{"algorithm":"hmac_sha256","format":"slingshot.continuation-token/1","key_identifier":"..."}` under canonical ordering, where the identifier is nonempty printable ASCII through MAXIMUM_CONTINUATION_KEY_IDENTIFIER_BYTES. Rotation retains the previous key for at least the token lifetime plus maximum clock skew; loss, unreadability, or an unknown key identifier fails integrity validation and never silently creates a new key while an old token may remain valid. The limits manifest's envelope-fit vectors construct the largest protected header and payload, account for canonical JSON escaping and base64url expansion, and prove they fit MAXIMUM_CONTINUATION_TOKEN_BYTES.

Validation precedence is exact and authenticates before trusting payload semantics. Over-bound/non-ASCII framing, segment count, base64url, protected-header canonical form/fields, or unusable key-identifier shape yields `continuation_token_malformed`; unknown key or constant-time tag mismatch yields `continuation_token_integrity_invalid`. Only after a valid tag, a noncanonical/unknown/missing/surplus payload field, key-identifier disagreement, invalid time relation/range, invalid limit, or invalid/over-bound resume key yields `continuation_token_malformed`; AuthorTargetIdentity mismatch then yields `continuation_token_wrong_target`; command/version/non-window-argument mismatch then yields `continuation_token_wrong_query`; only an otherwise matching authentic token at or after expires-at yields `continuation_token_expired`. Every failure is closed and carries only `failure`. A successful token reuses its protected Initial limit, resumes strictly after its repository-path sort key, and never reapplies the Initial offset. Pagination is page-at-a-time ordered rather than repository-snapshot-consistent: each page is strictly ordered while concurrent repository mutation can add, remove, or change matches in later pages. Plan 0005 must persist/configure the key lifecycle and execute these language-neutral vectors; Plan 0003 only validates opaque token bytes, payload-vector shape, and the declared failure inventory.

discovery_budget.rs owns the shared DiscoveryExecutionBudget counters, failure type, and named constants used unchanged by all six discovery commands. An inspected candidate charges one candidate node before any of its properties or criteria. Each scalar repository value encountered charges one property value; its byte charge is UTF-8 length for textual JCR types, eight for Long/Double, one for Boolean, and Binary length without materializing bytes. Each atomic selection test—including a PropertyPredicate, phrase comparison, template comparison, requested component/resource-type comparison, asset criterion, or reference resolution—charges one criterion evaluation. At every cooperative boundary the agent checks cancellation, then injected monotonic elapsed time, then the next checked count/byte charge. Boundaries occur immediately before and after anchor resolution, query/iterator advancement, property retrieval, reference resolution, and canonical-result construction steps. Elapsed time at or beyond MAXIMUM_DISCOVERY_EXECUTION_DURATION fails, while count/byte charges through their exact maxima succeed and the next charge fails. Checked arithmetic overflow is failure, never wraparound.

MAXIMUM_DISCOVERY_CANDIDATE_NODES, MAXIMUM_DISCOVERY_PROPERTY_VALUES, MAXIMUM_DISCOVERY_PROPERTY_BYTES, MAXIMUM_DISCOVERY_CRITERION_EVALUATIONS, MAXIMUM_DISCOVERY_EXECUTION_DURATION, and MAXIMUM_DISCOVERY_RESULT_BYTES are caller-independent. After a candidate fully matches, offset disposition occurs before result construction: a positive remaining Initial offset consumes that one match and continues without a result-byte charge; otherwise the next complete match is canonicalized and admitted. Result-limit or result-byte completion is checked immediately after admission and wins without charging another repository step; canonical response construction has its own cooperative boundaries. If admitting the next match would cross the byte maximum, the page completes before admitting it and carries a token after the last emitted match; the registry guarantee makes a zero-emitted-match byte completion impossible for legal inputs. A repository/query call that returns at or after the deadline produces `discovery_budget_exceeded` with `execution_duration` before its value or error is interpreted, and every accumulated match/token is discarded. A call that does not return cannot be preempted by this cooperative clock, so the contract makes no hard wall-clock completion claim; transport supervision may report a stalled job but cannot relabel it as a duration-budget failure. Cancellation observed at a boundary terminates the external job as cancelled, makes no command result or continuation token publishable, and stops every later repository call. Cancellation vectors prove that call trace and no-publication fact, not interruption latency inside a blocking call. A registry proof computes each command's largest legal single match plus complete success envelope and continuation token and requires it to fit MAXIMUM_DISCOVERY_RESULT_BYTES.

property_value.rs separates PropertyScalarValue from PropertyValue. PropertyScalarValue is String, Boolean, Integer, DecimalString, DateTimeString, or RepositoryPropertyPath. Integer is exactly the signed 64-bit JCR Long range and its canonical string grammar is `0|-?[1-9][0-9]*`: plus, leading zero, and negative zero are invalid. DecimalString is a scale-preserving plain-decimal JCR Decimal representation with an optional minus, integer part `0|[1-9][0-9]*`, and optional fraction containing one through MAXIMUM_DECIMAL_FRACTION_DIGITS digits. MAXIMUM_DECIMAL_INTEGER_DIGITS and MAXIMUM_DECIMAL_BYTES bound the remaining dimensions. Plus, exponent, omitted integer/fraction digits, leading integer zero, negative numeric zero, and excess integer/fraction/total bytes are invalid; fractional presence and trailing zeros are preserved because they carry JCR Decimal scale. Decimal comparison is arbitrary-precision numeric and never binary floating point. DateTimeString is Slingshot's supported interoperable UTC-millisecond subset of JCR Date, not the full Java Calendar range: it accepts only calendar-valid `YYYY-MM-DDTHH:MM:SSZ` when milliseconds are zero or `YYYY-MM-DDTHH:MM:SS.sssZ` when nonzero, where the year is 0001 through 9999, seconds are 00 through 59, and MAXIMUM_DATE_TIME_FRACTION_DIGITS is exactly three. Offsets, leap seconds, alternate fractional widths, and a zero `.000` suffix are noncanonical and invalid. RepositoryPropertyPath maps to the supported absolute-or-relative JCR Path subset, not String. PropertyValue is either one scalar or a non-empty bounded ordered collection of scalar values that all have the same discriminator; nested, empty, and mixed-type lists are invalid and map exactly to JCR multi-valued properties. Null and deletion are not variants. Mutation omission leaves a property unchanged.

PropertyName identifies one direct JCR property: it rejects slash, empty/dot/parent spellings, NUL, controls, and over-bound bytes while preserving valid namespace-colon spelling. Authoring commands accept only PropertyValue and cannot carry a configuration observation, redaction marker, or Open Service Gateway Initiative metatype evidence as repository content.

Canonical JCR property JSON uses these exact closed spellings. A scalar is `{"type":"string|boolean|integer|decimal|date_time|repository_path","value":...}`. String uses a JSON string and Boolean a JSON Boolean; Integer uses its canonical signed base-ten string so every JCR Long survives parsers without numeric truncation; Decimal, DateTime, and RepositoryPath use their validated strings. PropertyValue is `{"cardinality":"single","value":<scalar>}` or `{"cardinality":"multiple","values":[<scalar>,...]}`; every multiple value has the same `type`. Unknown, missing, and surplus fields are invalid. The separately defined configuration observation grammar never reuses this JCR mutation model.

RelativePropertyPath is a query-only non-empty slash-separated path serialized as one exact JSON string under the repository-role grammar above; it contains zero or more RepositoryPathSegment child addresses followed by one PropertyName. Predicates resolve that path from the candidate node without fallback, descendant search, or name aliasing. Mutation property maps accept PropertyName only and cannot address descendants.

Canonical predicate JSON uses the exact `operator` and field names: Exists is `{"operator":"exists","property_path":...}`; Equals and NotEquals use `equals|not_equals` plus `property_path` and one PropertyValue field named `value`; ScalarIn uses `scalar_in` plus `property_path` and a `values` array of homogeneous PropertyScalarValue; ListContainsAny and ListContainsAll use `list_contains_any|list_contains_all` with the same fields; LessThan, LessThanOrEqual, GreaterThan, and GreaterThanOrEqual use `less_than|less_than_or_equal|greater_than|greater_than_or_equal` plus `property_path` and one ordered PropertyScalarValue field named `value`. Every object is closed and rejects an operator-incompatible, unknown, missing, or surplus field.

search_predicate.rs defines the following closed, explicitly discriminated PropertyPredicate variants:

- Exists contains only a RelativePropertyPath and matches when that resolved property is present, including an explicitly empty repository multi-value.
- Equals and NotEquals contain one PropertyValue and require the same discriminator/cardinality. String and RepositoryPropertyPath use exact validated spelling, Boolean uses value equality, Integer and Decimal use mathematical equality, DateTime uses instant equality, and homogeneous lists compare element-for-element in repository order under those scalar rules.
- ScalarIn contains a non-empty ordered unique same-discriminator collection of PropertyScalarValue candidates and matches a scalar property equal to any candidate.
- ListContainsAny and ListContainsAll contain a non-empty ordered unique same-discriminator collection of PropertyScalarValue members and apply only to a same-discriminator list-valued property.
- LessThan, LessThanOrEqual, GreaterThan, and GreaterThanOrEqual contain one OrderedScalarPropertyValue. Integers and arbitrary-precision decimals compare numerically, date-time strings compare as instants, strings compare by Unicode scalar-value order, and unlike discriminators never compare.

RepositoryPropertyPath and list values are excluded from ordered comparisons. PackagePathSelectionExpression is a bounded absolute slash-separated token sequence. Each token is one exact RepositoryPathSegment, whole-segment `*`, or exact whole-segment `(.*)`. `*` consumes exactly one complete repository path segment; `(.*)` consumes zero or more complete segments and is legal at the beginning, middle, or end. All other accepted tokens are literal RepositoryPathSegment values compared by exact validated bytes: characters that a regular-expression engine might treat specially have no such meaning. Root `/` has no tokens and matches only root. Repeated/trailing slash, partial asterisk, `**`, or another segment containing an asterisk is invalid. The exact `/content/bar/(.*)/image` expression therefore matches `/content/bar/image`, `/content/bar/a/image`, and `/content/bar/a/b/image`, but not a path with a different literal prefix/suffix or trailing segment.

Matching uses no regular-expression engine, recursion, or backtracking. `MAXIMUM_PACKAGE_SELECTION_EXPRESSION_TOKENS` bounds expression tokens and the RepositoryPath contract bounds candidate segments. For one expression/candidate pair, a bottom-up Boolean dynamic-programming table has exactly `(token_count + 1) * (candidate_segment_count + 1)` cells under checked arithmetic and `MAXIMUM_PACKAGE_MATCHER_CELLS`; each cell is filled once in a fixed reverse row/column order. A literal or `*` cell consumes one segment and advances one token; an `(.*)` cell is true only from the already-computed zero-segment next-token cell or one-segment same-token cell. The final cell is true only when both sequences are exhausted, so matching is complete-path anchored. Language-neutral conformance vectors carry expression tokens, candidate segments, expected match, and exact charged cell count. Rust executes them in this plan, including the exact user-shaped expression, zero/one/many middle segments, multiple `(.*)` tokens, Unicode/literal metacharacters, root, and maximum/overflow boundaries; the artifacts are normative input to the separately owned external Java agent gate, but no Slingshot-repository test or done claim says that Java executed them.

FileVault filter generation never translates the user expression language into a regular expression. It starts only after bounded enumeration and restricted-matcher evaluation have produced finite, disjoint selected-node and structural-ancestor sets. Command exclusion expressions have already removed nodes and therefore emit no FileVault node-exclude expression. For each ascending command root, the generator orders retained node paths by segment depth and then UTF-8 bytes so every ancestor precedes its descendant, collapses duplicates, and emits an exact node include for each retained path. A selected node is serialized with all of its direct properties and is represented by its ordinary FileVault directory/`.content.xml` form. A structural ancestor is serialized as a ZIP directory entry only, has no `.content.xml` and no property value, and receives a following `matchProperties="true"` property-exclude rule matching all of its direct property paths. If a path is both structural and selected, selected wins and the property-exclude rule is absent. Thus structural ancestors enable export traversal but do not capture unrelated ancestor properties, children, or siblings. If a consumer later imports the package, an already-existing directory-only structural ancestor is not supplied replacement properties; a missing one may nevertheless be created by FileVault using its effective default child node type because hierarchy creation is intrinsic to importing the selected descendant. The package manifest records that consequence and does not describe structural entries as effect-free. An empty final selection emits each root with one fixed never-match include and no repository content entry.

The language-neutral `slingshot.filevault-filter/1` quoting algorithm takes one already canonical JCR path. It rejects a scalar outside XML 1.0 valid ranges with `filevault_filter_unrepresentable`. For a node include it produces Java-regex bytes `\A\Q<literal>\E\z`; for a structural-ancestor direct-property exclude it produces `\A\Q<literal>\E/(?:[^/]+)\z`. In either form it replaces every literal occurrence of `\E` inside the path with `\E\\E\Q` before adding the final `\E` and fixed suffix; this quotes dot, caret, dollar, asterisk, plus, question mark, parentheses, square/curly brackets, vertical bar, and backslash without relying on a platform `Pattern.quote` implementation. The fixed empty-selection expression is `\A(?!)\z`. Regex bytes are then XML-attribute escaped by scanning once and replacing an input ampersand with `&amp;`, less-than with `&lt;`, greater-than with `&gt;`, double quote with `&quot;`, and apostrophe with `&apos;`; generated entity bytes are never scanned again. Root attributes use the same XML-codepoint validation and entity escaping without regex quoting. Canonical UTF-8, double-quoted attributes, element/attribute spelling, root order, include order, and each immediately following structural-property exclude are fixed. The complete canonical filter and package manifest must respectively fit MAXIMUM_PACKAGE_FILTER_DOCUMENT_BYTES and MAXIMUM_PACKAGE_MANIFEST_BYTES before staging. Vectors include literal `(`, `+`, `^`, `$`, backslash, the two-scalar sequence `\E`, ampersand, both quote forms, both angle characters, supplementary Unicode, invalid XML scalars, overlapping roots, empty selection, and ancestor/selected property manifests.

Candidate enumeration and production are governed by checked deterministic units rather than an unenforceable wall-clock promise: MAXIMUM_PACKAGE_CANDIDATE_PATHS, MAXIMUM_PACKAGE_PATTERN_EVALUATIONS, MAXIMUM_PACKAGE_SELECTED_PATHS, MAXIMUM_PACKAGE_FILTER_DOCUMENT_BYTES, MAXIMUM_PACKAGE_MANIFEST_BYTES, MAXIMUM_PACKAGE_ARCHIVE_ENTRIES, MAXIMUM_PACKAGE_UNCOMPRESSED_INPUT_BYTES, and MAXIMUM_PACKAGE_OUTPUT_BYTES. One `pattern_evaluations` unit is charged before filling one matcher table cell; a cell through the exact maximum succeeds and the next cell fails without completing or publishing the candidate selection. Each distinct selected content path and structural ancestor consumes one `selected_paths` unit before admission. FileVault construction checks the next selected/structural path, filter byte, manifest byte, archive entry, input-byte, and output-byte charge before reading/writing it. The content-package artifact slot maximum equals MAXIMUM_PACKAGE_OUTPUT_BYTES. This contract makes no hard elapsed-time claim for blocking repository or FileVault library calls; transport supervision may diagnose a stalled job without misreporting a duration-budget failure.
