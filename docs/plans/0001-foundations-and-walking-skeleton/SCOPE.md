# Plan 0001 — Foundations and Walking Skeleton

> Establish the Rust workspace, its enforceable engineering contract, and a real command-line-to-daemon process boundary before any Adobe Experience Manager behavior exists.

## Why this plan

Slingshot begins as an empty repository, while every later capability depends on the same crate boundaries, naming rules, local process ownership, and test discipline. Deferring those decisions would let configuration, transport, command, and workflow work invent incompatible foundations. This plan therefore creates the complete workspace shape and proves the riskiest local boundary immediately: several clients addressing one profile and environment can converge on one daemon and receive a framed response.

Plan 0001 has no cross-bundle prerequisite and is the sole first candidate under the root sequential Phase R contract. Registration requires no other active bundle and binds the exact reviewed current commit containing this source-digest-matching bundle; that validation base must descend from the authored base recorded in `STATUS.md`. Abstract target declarations and an untrusted current-native report do not relax that base rule or authorize a later plan.

## In scope

- **0001 — Workspace Foundation.** Pin Rust 1.98.0 with edition 2024, resolver 3, and inherited workspace-wide `unsafe_code = "forbid"`; split the unpublished ten-crate/two-binary skeleton, complete the structural module-family ownership map plus compiling Plan 0001 leaf shells, serialize exhaustive development-command composition, freeze the candidate dependency inventory plus current-native probes, establish exact abstract target capability/artifact-layout rows, enforce dependency direction, and implement the platform runtime through independently falsifiable tasks before process features land. Later feature plans own their exact leaf inventories; Plan 0009 owns concrete all-row native mappings and authority.
- **0002 — Engineering Policy.** Add repository-local source-policy and quality gates for deterministic rejection of unsafe Rust syntax, full-word declared identifiers, named semantic and operational numeric constants, code files at or below 1,000 lines, cyclomatic complexity at or below 10, governed Structured Query Language migrations, contract-focused present-state documentation, immutable least-privilege workflow policy fixtures, formatting, linting, tests, dependency policy, reproducible lockfile use, exact-snapshot-only RustSec authentication, and deterministic supported-row policy fixtures.
- **0003 — Local Walking Skeleton.** Pin every Plan 0001 wire/security/interoperability/process limit in `support/foundation-contract.toml`; define retained ping plus nonce-bound cooperative stop; derive one runtime namespace per profile/environment; implement endpoint/lock equivalents including Windows remote-pipe rejection; enforce one daemon owner; make explicit concurrent daemon start converge on that owner; keep daemon ping existing-only; and clean tests through current-nonce stop or a retained stable child supervisor without PID signalling.
- **0004 — Present-State Documentation.** Publish the root README, CONTRIBUTING, and ARCHITECTURE documents for the workspace and walking skeleton that exist when this plan completes.

## Locked decisions

- The workspace contains `slingshot-domain`, `slingshot-configuration`, `slingshot-agent-protocol`, `slingshot-local-protocol`, `slingshot-agent-connection`, `slingshot-storage`, `slingshot-daemon`, `slingshot-command-line`, `slingshot-test-support`, and `slingshot-development`. The first eight are product crates; the final two support tests and repository policy.
- The `slingshot` executable lives in `slingshot-command-line`. Its process entry point stays thin and delegates to library code so process behavior remains integration-testable.
- Durable agent-job identifiers, states, per-job sequences, and target-stream cursors are inward domain vocabulary. `slingshot-agent-protocol` owns their wire representations and conversions, while `slingshot-storage` remains dependent only on `slingshot-domain`.
- Reusable path-only executable values and operating-system process harnesses, including `FiniteStateMachineExecutable`, live in `slingshot-test-support`. Source provenance, external builds, repository orchestration, and release commands live in outermost `slingshot-development`.
- `slingshot-development` exposes both its library and the repository-command binary used by checked-in quality and policy commands; the product binary remains `slingshot` in `slingshot-command-line`.
- One daemon owns one `(profile, environment)` runtime namespace. Clients for the same target converge on that daemon; distinct targets have independent daemon processes, endpoints, locks, and state.
- The walking skeleton accepts target names as bounded opaque values. Plan 0002 gives those names configuration meaning.
- The local transport uses the exact length-prefixed bounded JavaScript Object Notation contract embedded from `support/foundation-contract.toml`. Supported Linux and macOS targets use Unix domain sockets and separate operating-system owner/startup-election lock files. Supported Windows targets use current-user access-controlled named pipes whose every server creation includes `PIPE_REJECT_REMOTE_CLIENTS`, plus separate Windows owner/startup-election lock objects and process-detachment equivalents. The daemon holds only the owner lock for its lifetime; one explicit-start client holds the election lock through responsive ping or failure, and winner crash releases it so a successor rechecks connection/ownership before takeover. Readiness is atomic and namespace storage is accessible only to the current user. Standard output of ordinary command-line calls contains results only; daemon diagnostics use its log sink.
- `support/platforms.toml` is the only abstract supported-target authority and contains `x86_64-unknown-linux-gnu`, `aarch64-apple-darwin`, and `x86_64-pc-windows-msvc` rows with exact required provider-trust-decision, runtime, filesystem, build-policy, and artifact-layout capabilities. It contains no provider, runner image, concrete linker/system-root/software-development-kit digest, or aggregate success. Plan 0001 runs every row's deterministic policy fake and real native behavior only for the row matching the current environment, emitting at most one explicitly untrusted report. Plan 0009 maps/probes/authenticates every exact native environment before a release claim.
- Each abstract row fixes executable name/suffix, archive profile and flat membership, native smoke mode, required host/architecture class, endpoint/lock/security/detachment/supervision capabilities, and deterministic build-policy requirements. It does not claim concrete build inputs or output bytes. No task derives facts from a family label, compares binaries across targets, or treats cross-compilation/copied reports as support.
- The frozen dependency baseline includes safe APIs for Plan 0002's provider-record server-authentication trust decisions, explicitly supplied immutable root stores with no ambient/default-root merge, distinct identity-management and author client configurations, and its exact Linux POSIX-access-control-list, macOS extended-access-control-list, and Windows Security-Identifier/discretionary-access-control-list/reparse/file-identity configuration boundary. Native probes must distinguish unconditional trust from purpose/distrust/external-constraint/unevaluable/conflicting decisions, prove that an additional author root cannot enter the identity-management verifier, and exercise the filesystem APIs on their exact supported rows without repository-owned unsafe Rust.
- Every package is `publish = false`, and manifests omit license, license-file, and repository metadata because no owner-supplied values exist. Release artifacts remain gated until the owner commits an explicit SPDX/license-file decision and canonical repository URL; no plan infers either value.
- Declared project identifiers spell words in full. Standardized external spellings remain unchanged in wire strings, serialized field names, dependency APIs, and citations. An exact abbreviated signature declaration is structurally exempt only through the closed table of literal leading-`::` fully qualified external trait/supported-platform interface paths and locked dependency identities. Aliases, re-exports, inferred short paths, project-owned traits, inherent methods, and project-controlled locals inside the implementation are never exempt; the checker makes no compiler-HIR inference claim.
- Production/test Rust, repository-owned executable scripts, and Structured Query Language migrations contain no unnamed semantic, domain-bound, size, duration, retry, capacity, exit, or other operational numeric expressions. Intrinsic identity/index operations, protocol-structural syntax, compiler-required syntax, parsed fixture/version grammar, dependency versions, and independently authored data fixtures have structural allowances. The checker never requires meaningless constants such as a named replacement for an intrinsic zero index.
- Every repository-owned Rust, build, workflow, executable-script, and Structured Query Language code file stays at or below 1,000 physical lines. Rust/script functions and migration conditional expressions stay at or below the single policy value of 10 for cyclomatic complexity.
- Every workspace Rust target inherits `unsafe_code = "forbid"`; repository-owned Rust contains no unsafe block, function, trait, implementation, foreign block/function, or unsafe attribute, and neither lint allowances nor documentation can exempt one.
- Product documentation and Rust documentation describe the code that exists in their commit. Planning prose is kept under `docs/plans/`. Automation rejects exact configured task markers, placeholders, planning-only headings, missing exported-item documentation, and required structural sections; semantic accuracy, completeness, and non-narrating comment quality remain a mandatory review checklist rather than an automated inference.
- Repository workflows pin every nonlocal action by full commit digest, grant only explicit least privileges, disable checkout credential persistence, and never interpolate untrusted workflow expressions directly into a shell command. Only the release binary-provenance job may hold the exact additional `id-token: write` and `attestations: write` permissions for explicit file subjects; artifact-storage, package, and all other write permissions remain forbidden, and all quality jobs remain read-only.
- RustSec input is an exact origin/full-commit/tree pin accepted only from an explicitly named clean checkout. Plan 0001 records `exact_snapshot_only`: Git timestamps, wall time, age arithmetic, and a human-review field cannot create freshness. Pin proposals use the explicit nonmutating review command; Plan 0009 requires a new owner-approved record in the protected release run and binds it to authenticated provider release-time evidence.
- Public Rust interfaces document their current contract, invariants, side effects, and failure conditions where those facts apply. Inline comments exist only where a constraint is not already clear from the types and control flow; they do not narrate syntax. Reviewers apply those semantic rules explicitly, while automation checks only the falsifiable forms named above.

## Out of scope

- Reading profile files, interpreting credentials, or connecting to Adobe Experience Manager.
- Durable operation storage, remote job submission, server-sent events, command implementations, or artifact transfer.
- The Java `slingshot-agent` bundle or any code compiled for Adobe Experience Manager.
- Command-line operations beyond version, explicit daemon start, and existing-only daemon ping, and any Model Context Protocol behavior.
- Operating-system targets absent from `support/platforms.toml`; concrete runner/build-environment selection; authenticated all-row evidence; and any release-support claim before Plan 0009 has mapped, probed, and provider-attested every abstract row, including real Windows remote-client rejection.
- Any hosted continuous-integration provider, repository identity, or runner selector before Plan 0009's explicit owner-confirmed automation gate.
