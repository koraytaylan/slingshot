# Plan 0001 — Foundations and Walking Skeleton

> The workspace and one local request path, with policy encoded before feature code accumulates.

## Implementer orientation

Each task authors its acceptance fixtures or structural assertions before implementation. Source modules and manifests stay within the task's `touches` boundary, and every task finishes with the workspace formatting, linting, and test gates. The dedicated module-map task declares crate and module-family roots plus documentation-only shells for the exact Plan 0001 source leaves before dependency-ordered tasks implement them; later feature plans own their exact leaf inventories. The inventory task proposes exact external-dependency candidates, and the probe task alone may correct and freeze them after deterministic policy/API coverage plus real behavior on at most the row matching the current native environment. Plan 0009 owns exact all-row machine mappings and authenticated aggregation.

The dependency direction is inward toward stable contracts:

| Crate | Responsibility | Product dependencies |
|---|---|---|
| `slingshot-domain` | Value objects, operation and durable agent-job vocabulary, execution ports, errors, and limits | none |
| `slingshot-configuration` | Profile documents, target resolution, and credential references | domain |
| `slingshot-agent-protocol` | Language-neutral author-agent messages, schemas, and wire conversions for domain job values | domain |
| `slingshot-local-protocol` | Daemon request, response, event, and framing contracts | domain |
| `slingshot-agent-connection` | Authentication and Author network transport | configuration, agent protocol, domain |
| `slingshot-storage` | Operation ledger and artifact persistence | domain |
| `slingshot-daemon` | Target-scoped application service and local server | all inward product adapters except command line |
| `slingshot-command-line` | Binary, command-line adapter, daemon client, and standard-input/output server | local protocol, configuration, daemon |
| `slingshot-test-support` | Fake services, virtual time, temporary roots, path-only executable values, and reusable process harnesses | domain, agent protocol, local protocol, and storage only |
| `slingshot-development` | Repository policy, external-source provenance and builds, orchestration, compatibility, hardening, and release commands | product crates and test support as the outermost tooling layer |

The first eight crates form the product graph and follow the inward edges in this table. A product crate may use `slingshot-test-support` only as a development dependency; no normal or build dependency from product reaches either support crate, and no other crate depends on `slingshot-development`. The test-support crate may depend normally only on the listed inward product contracts/adapters, never on daemon, agent connection, configuration, command line, or development. Reusable process harnesses accept paths and plain process inputs instead of outer-crate types. `FiniteStateMachineExecutable` is a path-only test-support value; development verifies provenance and builds the external executable before constructing it. Development is the outermost layer and may depend inward on product and test support for repository-only commands and tests. The workspace dependency check reads Cargo metadata with dependency kinds and rejects every absent edge and every cycle.

Durable remote-work vocabulary follows the same rule. `AgentJobIdentifier`, `AgentJobState`, `JobEventSequence`, and `EventStreamCursor` live in `slingshot-domain`; protocol adapters validate and convert their wire encodings, and storage persists the domain values without an edge to `slingshot-agent-protocol`.

## 0001 — Workspace Foundation

Task `workspace-scaffold` creates only a virtual workspace with `resolver = "3"`, shared edition `2024`, `rust-version = "1.98.0"`, an inherited workspace lint table with `unsafe_code = "forbid"`, ten minimal library members, the product `slingshot` binary, the `slingshot-development` repository-command binary, and a committed dependency-free lockfile. Every member is `publish = false`. Workspace and member manifests omit license, license-file, and repository fields because this repository has no owner-supplied legal decision or canonical remote; a release artifact remains gated until those values are explicitly committed, and no value is inferred from another project. `rust-toolchain.toml` pins the same compiler and includes formatting and linting components.

Task `workspace-module-map` separately creates the documented crate and module-family tree named throughout Plans 0001–0009 and every exact Plan 0001 daemon, command-line, test-support, and development library leaf. A checked fixture maps every structural root and Plan 0001 leaf to one crate/layer. Domain roots include durable agent-job vocabulary, protocol roots include wire conversions, and test-support roots include generic process harnesses and path-only executable values. Each Plan 0001 leaf begins as a compiling documentation-only shell; its dependency-ordered behavior task replaces that shell without needing an undeclared module. Auto-discovered binary entries, local-protocol leaves, and platform-runtime family leaves remain with their behavior owners. The domain `command` root is established here, while Plan 0003 task `command-module-scaffold` alone owns the exact command leaf inventory and adds those leaf declarations/files. These standard-library-only structural modules establish stable merge paths without placeholder behavior or dependency selection.

Task `workspace-capability-inventory` owns the initial `policy/workspace-capabilities.toml`, lockfile, and root/member manifest candidates. It maps each structural module family and each explicitly named planned capability consumer to its normal, build, and development dependency capabilities and records an explicit standard-library or empty set where a dependency kind is unused. Feature plans may refine their own leaf inventories without creating a second dependency-version authority. The inventory covers typed error/serialization/TOML/JavaScript Object Notation; identifiers/URLs/digests/Base64/secrets; asynchronous runtime/cancellation/bytes; Hypertext Transfer Protocol client and fake-author server; additional-certificate TLS plus supported-platform root enumeration that exposes provider-record DER and effective server-authentication purpose, distrust/deny, external application/policy/name constraints, and evaluability without lossy reduction; signed assertions; SQLite with the pinned bundled engine; command-line/diagnostics/schemas; supported-platform directories, locks, Unix sockets, Windows named-pipe creation with `PIPE_REJECT_REMOTE_CLIENTS`, detachment, and stable child supervision; descriptor-relative no-follow configuration-file traversal and identity; native access-control/file-identity APIs; deterministic archive/checksum APIs for Plan 0009; policy parsing; temporary files; property tests; and process assertions. Native rows expose only safe Rust APIs compatible with `unsafe_code = "forbid"`; archive rows do not implement release packaging here. Every registry package, exact version, feature/default-feature choice, target condition, and dependency kind is centralized under workspace dependencies.

Task `supported-platform-matrix` creates `support/platforms.toml` as the abstract target authority with exactly `x86_64-unknown-linux-gnu`, `aarch64-apple-darwin`, and `x86_64-pc-windows-msvc`. Rows declare exact native operating-system/architecture requirements, provider-record server-authentication trust-decision capability, endpoint/lock/current-user/detachment/stable-supervision capabilities, executable/suffix/archive/smoke layout, and deterministic build-policy requirements. The Windows row requires the named-pipe remote-client-rejection flag. Concrete provider selectors, images, linker/system-root/software-development-kit digests, environment values, and aggregate success are invalid here. Plan 0001 evaluates every row through deterministic policy fakes and may emit at most one untrusted observation for the current matching native environment. Plan 0009 owner-gates exact native mappings, complete build inputs, real all-row probes, and two-build/archive evidence.

Task `workspace-capability-probes` adds one probe per inventory row. Probes compile on Rust 1.98.0 with exact features and exercise public APIs. Provider-trust probes must distinguish an unconditional server-authentication root from distrust, purpose restriction, externally represented application/policy/name constraint, unevaluable state, and conflicting same-DER records; a certificate-only list is not a passing capability. TLS probes must also build two explicit immutable stores without ambient/default-root discovery and prove that a root supplied only to the author configuration cannot authenticate the identity-management configuration. Target-conditioned policy fakes run for all abstract rows; real target-specific behavior runs only for the row matching the current environment and yields an `untrusted_current_native_observation`. Windows API coverage includes the required pipe flag and stable supervision; no process identifier is later used as signal authority. A failing candidate is replaced atomically across inventory, manifests, lockfile, and probes. A fixture rejects uncovered/unused rows, feature/dependency drift, unsupported compiler, copied/cross-compiled native evidence, or an aggregate claim.

Task `dependency-direction-check` implements a development command that consumes `cargo metadata --locked --format-version 1`. It compares direct local-package edges and dependency kinds with the rules above, rejects cycles and undeclared edges, and reports both crate names, dependency kind, and forbidden direction. Its tests use small metadata fixtures rather than the live workspace alone, so rejection behavior is independently proved.

Task `platform-runtime-contract` implements operating-system behavior after the canonical foundation contract, abstract matrix, and capability proofs. Every namespace has a daemon-lifetime owner lock and a distinct explicit-start election lock. Linux/macOS use Unix advisory locks, Unix sockets, owner-only runtime directories, atomic readiness, and session-independent detachment. Windows uses exclusive lock objects and current-user access-controlled named pipes created on every path with `PIPE_REJECT_REMOTE_CLIENTS`, plus atomic readiness and detached creation without inherited protocol streams. The elected client never lends its lock to the daemon; winner exit releases only election, and a successor reconnects/revalidates before takeover. Test support retains a private supervisor owning the exact unreaped child/native handle until one atomic exit-or-terminate-and-wait disposition; numeric process identifiers are diagnostics only. Deterministic fakes cover all rows, real conformance runs only for the current matching row, and its report is explicitly untrusted until Plan 0009 reruns and provider-attests every owner-mapped row. A current-native Windows remote-client attempt is required when an explicit remote fixture exists; otherwise only the mandatory flag fixture passes and release proof remains unavailable.

## 0002 — Engineering Policy

Task `source-policy-checker` implements `cargo run --locked -p slingshot-development -- source-policy`. It parses repository Rust plus repository-owned executable script and workflow code and enforces:

- no repository-owned Rust, build, workflow, executable-script, or Structured Query Language migration code file exceeds the named `MAXIMUM_CODE_FILE_LINES` value of 1,000;
- locally declared Rust items, fields, parameters, variables, methods, modules, generic parameters, and explicit lifetime names plus script functions and variables contain no single-character name and no token from `policy/abbreviated-identifiers.txt`; the maintained entries include common shortenings such as `id`, `req`, `resp`, `cfg`, `config`, `env`, `auth`, `cred`, `ctx`, and local acronym spellings for the external protocols;
- semantic, domain-bound, size, duration, retry, capacity, exit, and other operational numeric literals occur only in named Rust constant or static definitions, enum discriminants, or named readonly script values; intrinsic identity/index operations, protocol-structural and compiler-required syntax, standardized workflow keys, external action versions, parsed fixture/version grammar, and independent fixture data have documented structural allowances rather than line exemptions;
- each Rust, executable-script, or migration function/expression stays at or below the repository cyclomatic-complexity ceiling of 10, stored once as `MAXIMUM_CYCLOMATIC_COMPLEXITY` policy data, and reports its symbol or statement when it exceeds that value;
- every repository-owned Rust target is covered by inherited `unsafe_code = "forbid"`, and syntax-aware policy rejects unsafe blocks, functions, traits, implementations, foreign blocks/functions, and unsafe attributes without an allow/expect escape hatch;
- Rust documentation and product Markdown contain none of the exact configured task-marker tokens, placeholder macros/text, or planning-only headings; `docs/plans/**` is excluded because it is intentionally prospective;
- repository workflows pin each nonlocal action reference to a full commit digest, declare explicit least-privilege permissions, disable credential persistence for checkout, and reject untrusted workflow expressions in shell `run` text or shell-reaching environment values; only the exact release binary-provenance job may add `id-token: write` plus `attestations: write` to `contents: read` for explicit file subjects, with no artifact-storage, package, or other write permission;
- exported Rust items carry nonempty documentation and configured machine-checkable documentation forms are present; whether prose accurately explains contracts, invariants, side effects, errors, bounds, and non-obvious constraints without narrating adjacent code is an explicit review checklist rather than a source-policy inference;
- placeholder bodies such as unconditional `unimplemented!`, `todo!`, or placeholder panics are absent from product code.

Repository-owned Structured Query Language migrations are code under the same contract. The checker parses them with a Structured Query Language grammar, applies the 1,000-line limit, rejects abbreviated locally declared table/column/index/trigger/view names, rejects unnamed semantic and operational numeric expressions outside the same structural fixture/version allowances, and computes branching complexity for triggers and conditional expressions against the shared ceiling. The checker examines declared project identifiers rather than dependency-owned symbols, standardized workflow keys, external action inputs, command names, or wire strings.

The full-word rule has one structural Rust exception described by `policy/external-interface-identifiers.toml`. Each entry binds an exact leading-`::` fully qualified external trait or supported-platform interface path, its locked external package or standard-library identity, the exact required item/signature spelling, and any exact target condition. An implementation receives the exception only when its source header literally uses that canonical path and its dependency identity matches locked Cargo metadata; imported aliases, renamed paths, re-exports, glob imports, local lookalikes, and inferred short paths are rejected rather than resolved. This is a closed interface table, not a general abbreviation allowlist and not a compiler-HIR claim. Only the exact required signature declaration is exempt; project-controlled local declarations in its body remain checked. The same spelling on an inherent method, a project-owned trait or its implementation, or an unrelated declaration is rejected. The test corpus includes accepted external `::core::fmt::Display::fmt` and exact fully qualified Serde visitor implementations, rejection through aliases/re-exports or on project-owned methods, and rejection of an abbreviated body-local inside an otherwise exempt implementation, alongside exact line and complexity boundaries.

Task `quality-automation` adds one argument-free repository-local sequence whose fixed Rust gates are format-all check; locked workspace check, lint, and test across all targets/features; and locked all-feature workspace rustdoc with warnings denied and dependencies excluded. It then runs pinned executable-script linting, migration/workflow policy, both development policy commands, dependency advisories/licenses, and clean-graph checks. `support/repository-tools.toml` pins each tool. Cold/warm harnesses exercise the same command; platform fakes cover every row and native capability/runtime/walking commands run only for the current matching environment. Plan 0009 alone owns owner-confirmed hosted adapters, exact all-row mappings, and attestation. Workflow policy remains fixture-tested: immutable action commits, disabled checkout credential persistence, explicit least privilege, and no untrusted expression in shell flow.

Task `rustsec-advisory-pin` authenticates an exact snapshot only. `compatibility/rustsec-advisory-database.toml` pins canonical origin, full commit, and canonical tree digest; its schema rejects timestamp, age, freshness, or review fields. The verifier accepts only `SLINGSHOT_RUSTSEC_ADVISORY_DATABASE_DIRECTORY`, proves exact detached clean bytes, and never discovers/fetches/repairs/advances a cache. `rustsec-pin-review` proposes verified pin bytes without time or freshness claims. Plan 0009's owner-protected release run creates a new exact-pin review record, binds it through the release cache, and authenticates it with provider release-artifact evidence. Replaying that evidence later proves historical review for that release, never current freshness.

## 0003 — Local Walking Skeleton

Task `minimal-local-protocol` owns `support/foundation-contract.toml`, format `slingshot.foundation-contract/1`, as the only numeric/enum source for Plan 0001 retained-control version/framing, identifier/error/name/namespace/nonce/readiness/endpoint bounds, Windows remote-client policy, connection capacity, server/start/stop/supervision deadlines, scheduling tolerance, and 20-client process cohort. Exact values are embedded and parsed through `slingshot-local-protocol`; repository bytes, embedded bytes, production code, fixtures, scripts, and tests must agree without source magic values. This manifest does not own Plan 0003 command leaves or command-contract limits. The retained envelope supports `daemon.ping` and `daemon.stop`. Ping returns the diagnostic process identifier and current 32-byte nonce; stop requires that nonce, acknowledges before orderly shutdown, and refuses a stale instance without side effects.

Task `daemon-runtime-ownership` derives manifest-bounded endpoint/lock names from full target values and the exact SHA-256 rule. The owner lifetime value holds its lock and random readiness nonce; readiness/process fields are diagnostics, not signal authority. Stop authorization compares only the live nonce. Stale records/Unix socket nodes are removed only after owner-lock absence proof; named-pipe lifetime follows server handles. Drop removes only its matching nonce record, so a stale nonce cannot affect a replacement even if a fixture reuses a numeric process identifier.

Task `daemon-ping-service` binds only while holding ownership, publishes readiness after ping is live, and dispatches bounded ping plus nonce-bound stop under the exact embedded connection/deadline values. A current stop nonce acknowledges then shuts down; stale returns `stale_daemon_instance`. Slow/incomplete/nonreading peers release capacity, while an established idle connection has no partial-frame deadline. Target values never change and distinct namespaces bind concurrently.

Task `concurrent-explicit-start` assigns convergence only to explicit `daemon start`: connect, elect, reconnect/revalidate, then one absolute detached spawn under manifest deadlines. The elected client retains election through responsive ping or terminal failure; successor takeover reconnects first and spawns only after absence proof. Successful starts return the same current nonce and diagnostic PID. Existing-only `daemon ping` never elects or spawns.

Task `walking-skeleton-process-proof` releases exactly the manifest's 20 clients behind one barrier and proves one nonce/owner, elected-starter crash takeover, slow-peer capacity release, second-target isolation, and existing-only ping. Each test daemon has a private supervisor retaining the exact unreaped child/native handle. Responsive cleanup uses current-nonce `daemon.stop`; deliberate unresponsiveness uses one supervisor terminate-and-wait operation. Neither path checks a PID and later signals it. After lock/process exit, ping proves absence and a new cohort creates a fresh nonce; stale nonce/supervision tokens cannot affect it even under a reused-PID fixture. All deadlines/tolerances come from the manifest, use monotonic waits, and use no fixed sleep. Only the matching current-native run emits an untrusted platform observation; Plan 0009 owns authenticated all-row proof.
